BH 실효 컷오프가 6.0e-04 라 경계 케이스가 탈락하고, BH 는 step-up 이라 발견이 줄면

**병목은 관문③이 아니라 관문②다.** 오탐이 0%인 것이 "없는 걸 만들지는 않는다"는 증거.

### 실행 조건

`--mode batch`(기본)로 측정했다. 운영(워커)은 건당 호출이라 조건이 다르며, 동등성
근거는 실험③ 비교였으나(aspect_f1 0.9899→0.9933, exact_match 0.9767→0.9766),
대표 지표가 aspect_f1에서 ①②(부정 판별 정확도·부정 한정 aspect 정확도)로 바뀐
뒤로 **이 동등성이 새 대표 지표 기준으로는 아직 재검증되지 않았다**(PR 리뷰 반영,
2026-08-05) — aspect_f1 기준 근거는 여전히 유효하지만, ①②(특히 FPR) 기준으로도
batch=per_item인지는 별도 확인 필요. **측정이 아니라 가정**이므로 리포트가 매 실행
이 문구를 출력한다.
운영과 완전히 같은 조건은 `--mode per_item`(≈$34.3).

## ③ 실측 결과 (2026-08-05 · classify_aspect_v5 · --only-negative · 배치)

**대표 지표는 aspect_f1이 아니라 ①②다(2026-08-04 지인님 A안 확정)** — 이상탐지가
실제로 소비하는 값은 sentiment=-1뿐이라, 중립 포함 전체를 재는 aspect_f1은 대시보드·
리포트용으로 용도를 내리고 병기만 한다.

⚠️ **둘 다 "완전히 온전한" 실행은 아니다** — 300건 표본은 규모가 작아 신뢰구간이
넓고, 전체(96,531건) 실행은 중간에 배치 실패로 55건(0.06%)이 무응답 처리됐다.
서로 다른 한계가 있는 두 실행을 같이 놓고 봐야 한다.

| 지표 | 300건 표본(seed=20, 부정150+비부정150) | 전체(96,531건, seed=42) |
| --- | --- | --- |
| 채점 건수 | 300 (무응답 0) | 96,476 (무응답 55, 0.06%) |
| ① 부정 판별 P / R / F1 | 100.0% / 97.3% / 98.7% | 99.1% / 96.8% / 97.9% |
| ① **FPR(오탐률)** | 0.0% (fp=0, tn=150 — 아래 검정력 주의) | **0.07%** (fp=65, tn=89,307) |
| ② 부정 한정 aspect accuracy | 99.3% | 98.9% |
| [대시보드용] aspect_f1(중립 포함) | 97.7% | 96.6% |

**규모가 다른 두 실행이 서로를 검산한다** — 표본을 322배(300→96,531)로 늘려도
recall 97.3%→96.8%, ② 99.3%→98.9%로 이탈이 작다. 300건 결과가 우연이 아니었다는
근거가 된다.

⚠️ **단, FPR만은 300건으로 판정할 수 없다.** 오탐은 특정 템플릿 하나에서만 나오는데,
그 템플릿이 비부정 150건 표본에 기대 6.8건 들어오고 뒤집힘률이 1.60%라 **기대 오탐이
0.11건**이다. 실제 오탐이 있어도 300건에서 FPR=0%가 나올 확률이 90%다. 300건의
`FPR 0.0%`는 "오탐이 없다"가 아니라 **"볼 검정력이 없다"**로 읽어야 하고, FPR 판정에는
전량이나 해당 템플릿 과표집 표본이 필요하다.

⚠️ **전체 실행의 오탐 65건은 전부 같은 문장이다** — `"배송 조회가 안 되는데 확인
부탁드려요."`(코퍼스 4,058건, 골든 `기타/0`). 이 문장은 프롬프트 예시20에 `기타/0`으로
그대로 인용돼 있는데도 1.60%(65/4,058)가 부정으로 샌다. 38행 최우선 규칙("부정적 경험이면
무조건 부정")이 밀고 있기 때문이다.

즉 예시20은 이 4,058건을 중립으로 붙들고 있는 **앵커**다. 리뷰에서 지적된 "분자 +57%"는
현재 수치가 아니라 **이 앵커를 제거했을 때의 상한**이며, 오탐이 전부 그 템플릿에서 나온다는
사실이 오히려 그 경고의 근거다. 따라서 few-shot 유출은 프롬프트 예시를 바꾸는 대신
평가에서 거르는 방향으로 처리한다(노션 [실험③ 지표 재설계] §6).

⚠️ **표본 설계 주의** — `--only-negative`는 부정 N + 비부정 N을 균형 추출한다(PR
리뷰 반영, 2026-08-05). 부정만 뽑으면 fp·tn이 구조적으로 0이 되어 "모든 문의를
부정으로 뭉개는" 모델도 precision 100%가 나오는 함정이 있었다 — 지금은 FPR까지
같이 측정된다(`tests/test_run_classify_eval.py`에 회귀 테스트로 고정됨).

⚠️ **전체 실행의 55건 무응답은 배치 실패**(API 처리 중 토큰/연결 문제로 일부 청크
누락)이지, 프롬프트나 채점 로직 문제가 아니다 — `run_classify_eval.py`가 실패
청크를 무응답으로 격리해서 나머지 96,476건 채점을 정상 진행했다(PR 리뷰 반영
전이었다면 청크 전체가 무응답 처리됐을 상황).

서영님 실험②가 지적한 "감성 322건(6.5%) 오판" 중 핵심 패턴(질문형 종결에 속아

## ⑤ 실측 결과 (2026-07-29 · gpt-4o-mini)

| 지표 | 결과 | 비고 |

| Grounding precision (RAG 있음) | **4/4** (100%) | copy_draft 라우팅 4건이 분모 |

**읽는 법 두 가지.**

- **RAG 유무 대조가 이 실험의 핵심.** RAG 없이 원인 라벨만 주면 LLM은 상세페이지에
  있지도 않은 문구를 지어냈다(0/4). 근거를 붙이자 4건 전부 실제 원문을 인용했다.
- **재시도 분포가 두 번째로 의미 있다.** 4건이 1차 실패 후 재시도로 통과했다 =
  재시도 temperature 상승·실패 피드백 로직이 라이브에서 실제로 작동한다는 증거.

**한계 (인용할 때 반드시 같이 말할 것).**

- 표본이 작다 (n=15 / 11 / 4). 100%는 "완벽"이 아니라 "아직 실패를 못 봤다"다.
- 라우팅 정확도는 원인 라벨 이름 자체가 답을 암시한다(`사진_색감_오차`에 "사진").
  판단력 테스트라기보다 **"지시 따르기" 테스트**에 가깝다.
- consistency·actionability는 프롬프트가 지시하는 항목을 채점해서 순환적이다.
- 컬렉션2(반려사유) 지표는 HITL 실사용 전까지 **구조적으로 측정 불가**.

설계 의도(왜 이렇게 재는지)는 `run_recommendation_eval.py` 소스의 docstring에 있다.

## 비용 통제 4원칙

1. **반복 실험은 oracle 모드로** — 정답 라벨을 직접 입력해 LLM 을 안 태운다 ($0)
2. **분류는 배치 호출** — 건당 호출하면 비용 2배 + 속도 제한 초과
3. **분류 결과는 시드별 캐싱** — 같은 걸 두 번 돌리지 않는다
4. **모델 티어링** — 호출 많은 분류는 저가 모델, 호출 적고 중요한 개선안 생성만 상위 모델

## 원칙

- **`data/golden/` 은 `eval/` 만 읽는다.** `app/` 코드가 import 하면 컨닝이다.
- **재현 가능해야 한다** — 결과와 함께 **실행일·모델명·프롬프트 버전·시드·표본 수 n**
  다섯 개를 반드시 기록할 것. 하나라도 빠지면 발표에 못 쓴다.
- **분모를 밝힐 것.** "100%"가 아니라 "15/15 (100%)"로.
- **정답지를 우리 코드로 만들지 말 것.** 채점 대상으로 정답을 만들면 자기 코드로
  자기를 채점하는 순환이 된다 (①의 `build_golden_anomaly.py` 참고).
