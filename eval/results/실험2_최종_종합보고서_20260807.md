## 0. 문서 목적

이 문서는 실험 2 데모 탐지 성능과 헛알림률 문제를 분석하면서 우리가 무엇을 했고, 어떤 결과가 바뀌었고, 어떤 가설이 맞았거나 틀렸는지를 한 문서 안에 정리한 최종 종합 기록이다.

## 1. 최종 결론

현재까지 확인한 결론은 다음과 같다.

1. 실험 2의 높은 헛알림률은 프롬프트/분류기 문제가 주원인이 아니다.
2. 남은 false 대부분은 oracle/golden에서도 발생하므로, 모델 오답보다 mock data 생성기의 `BASELINE_RATE` 해석 문제가 핵심이다.
3. 초기 헛알림률 64.0%는 채점 제외 window 6건을 false로 세고 있었기 때문에 공식 채점 기준으로는 60.9%로 정정된다.
4. 이 60.9%는 성능 개선값이 아니라 채점 정정값이다.
5. mock data 공식 재생성, threshold 튜닝, prompt 수정, warmup/shadow/gating 채택은 아직 하지 않았다.
6. 다음 단계는 모델 튜닝이 아니라 팀 차원의 `BASELINE_RATE` 의미 확정과 생성기 보정 여부 결정이다.

## 2. 중요한 윤리·방법론 기준

이번 분석에서 지킨 기준:

- 공식 `data/input`, `data/golden`을 재생성하지 않았다.
- 성능 숫자를 좋게 만들기 위해 threshold를 바꾸지 않았다.
- prompt를 수정하지 않았다.
- warmup, shadow, CS 색상 gating 같은 정책 후보를 최종 성능 개선으로 채택하지 않았다.
- 평가셋을 보고 만든 규칙을 같은 평가셋 성능으로 홍보하지 않았다.
- “성능 개선”과 “채점 정정”을 구분했다.

따라서 현재 결과는 모델을 개선했다는 결과가 아니라, 평가 기준과 mock data 문제를 분해한 결과다.

## 4. 우리가 실제로 수정한 것

### 4.1 `demo_sim.py` 채점 기준 수정

기존에는 `intended_answer == TRUE`만 true로 보고, 그 외 발행 알림은 대부분 false로 처리했다.

문제는 `config_anomaly.csv`에 다음과 같은 시나리오가 존재한다는 점이었다.

- `scoring_included=N`
- `intended_answer` 빈칸
- 의도적으로 채점에서 제외한 관찰/보류/구분불가 케이스

이런 구간에서 알림이 발생하면 원래 공식 false로 세면 안 된다. 그래서 다음과 같이 분류를 확장했다.

| 분류 | 의미 |
|---|---|
| true | TRUE window 안에서 발생한 알림 |
| echo | TRUE window 이후 6일 tail 안에서 발생한 늦은 알림 |
| ignored | scoring 제외 또는 intended_answer 빈칸 window와 그 이후 6일 tail 안에서 발생한 알림 |
| false | 위 어디에도 해당하지 않는 알림 |

수정 결과:

| 지표 | 수정 전 | 수정 후 |
|---|---:|---:|
| 발행 알림 | 75 | 75 |
| 채점 대상 알림 | 75 | 69 |
| true 알림 | 27 | 27 |
| ignored 알림 | 0 | 6 |
| false 알림 | 48 | 42 |
| 헛알림률 | 64.0% | 60.9% |
| 케이스 도달률 | 20/26 | 20/26 |

판단: 이 변화는 성능 개선이 아니라 채점 정정이다.

ignored 6건 세부 확인:

로컬 `config_anomaly.csv` 기준 scoring 제외 또는 intended blank 행은 21개이고, 그중 config 설계 상승폭이 3%p 이상인 행은 12개였다. 이번 demo에서 ignored로 분리된 6건은 모두 config_delta 6.5%p 이상인 scoring 제외/blank 구간과 매칭되었다.

| 51 | P028 | cs | 사이즈 | ALL | 7.00%p | SC-027 NAVER/ZIGZAG 46-52, intended blank |

## 5. false 48건의 최종 분해

초기 false-like alert 48건은 다음과 같이 분해된다.

```text
초기 false-like 48건
├─ ignored 6건
└─ 남은 false 42건
   ├─ early_same_channel 30건
   │  └─ 30/30 모두 미래 TRUE case-past와 현재 window overlap
   └─ no_true_same_product_aspect_source 12건
      ├─ 미래 채점 제외 same PAS case-past 6건
      ├─ 미래 scored FALSE same PAS case-past 2건
      ├─ 같은 상품의 다른 aspect case-past 2건
      └─ 명확한 config overlap 없는 배경 변동 row 2건
```

요약하면:

- 6건은 공식 false가 아니라 ignored다.
- 남은 42건 중 40건은 baseline 희석으로 생긴 config case-past 경계 단차와 관련된다.
- 남은 2건도 oracle/golden에서 발생하므로 분류기 문제는 아니며, 배경 변동 또는 hot/gap 생성 영향으로 보인다.

## 6. 단계별 가설 검증

### 가설 1. “헛알림률 64.0%는 그대로 공식 성능이다”

판정: 틀림.

근거:

기존 false 48건 중 6건은 `scoring_included=N` 또는 빈 `intended_answer` window와 겹쳤다.

이 구간은 사전에 채점 제외로 설계된 구간이므로 false로 세면 안 된다.

결과:

- false-like: 48
- ignored: 6
- 공식 false: 42
- 헛알림률: 64.0% -> 60.9%

주의:

60.9%는 성능 개선이 아니라 채점 정정이다.

### 가설 2. “헛알림의 주원인은 프롬프트/분류기 오답이다”

판정: 대부분 틀림.

검증 방법:

남은 false 42건을 real classification 결과와 oracle/golden 결과로 각각 비교했다.

결과:

| 구분 | 개수 |
|---|---:|
| oracle/golden에서도 같은 날 발생 | 41 |
| real classification에서만 발생 | 1 |

해석:

42건 중 41건이 oracle에서도 뜬다. 따라서 현재 큰 헛알림 덩어리는 프롬프트가 잘못 분류해서 생긴 문제가 아니다.

남은 real-only 1건도 같은 상품의 다른 aspect case-past 영향과 겹치므로, 완전한 프롬프트 단독 문제로 보기 어렵다.

### 가설 3. “CS 색상 프롬프트가 문제라서 헛알림이 많다”

판정: 초반 관찰로는 그럴듯했지만, 최종적으로는 주원인으로 보기 어렵다.

초기 관찰:

- CS false-like alert: 44/48
- 색상 false-like alert: 41/48
- CS 색상 false가 매우 많아 보였다.

추가 검증:

하지만 남은 false 대부분이 oracle/golden에서도 발생했다. 즉 분류기가 색상을 잘못 잡아서 생긴 문제가 아니라, golden label 기준 데이터 자체에서도 탐지가 발화했다.

결론:

CS 색상에 현상이 집중된 것은 맞지만, 주원인은 프롬프트가 아니라 mock data 생성기의 baseline 해석 문제다.

### 가설 4. “baseline 생성이 희석되고 있다”

판정: 맞음.

검증 방법:

순수 배경 상품만 따로 떼어 golden label 기준 부정률을 측정했다.

결과 예시:

| Channel | Aspect | 순수 배경 관측 | Config |
|---|---:|---:|---:|
| COUPANG | 색상 | 0.903% | 5.000% |
| NAVER | 색상 | 1.042% | 6.000% |
| ZIGZAG | 색상 | 0.972% | 7.000% |
| NAVER | 사이즈 | 1.667% | 9.000% |
| ZIGZAG | 소재 | 0.903% | 6.000% |

원인:

생성기가 전체 문의 수에 baseline을 적용하는 것이 아니라, 먼저 aspect별로 문서를 나누고 그 내부에서 baseline 확률을 적용한다.

따라서 전체 분모 기준으로 보면 대략 `config / aspect_count`처럼 희석된다.

중요한 해석:

이 문제는 확정이다. 추가 검산 결과, 이 문제는 아래 가설 6의 `case-past` 조기 발화와도 별개 원인이 아니라 같은 생성기 문제의 다른 현상으로 보는 것이 더 정확하다.

추가 검산:

`TRUE` config 행 33개 각각의 `ws-28 ~ ws-1` case-past 구간을 golden label 기준으로 다시 세었다.

| 항목 | 값 |
|---|---:|
| TRUE config 행 | 33 |
| case-past 관측률이 config `past_neg/past_total`과 일치 | 33/33 |
| config `past_rate`가 `BASELINE_RATE`와 일치 | 33/33 |
| 평균 case-past 관측률 | 5.03% |
| 평균 config past_rate | 5.03% |
| 평균 순수 배경률 | 0.85% |
| 평균 config / 순수 배경 비율 | 6.04배 |

해석:

case-past는 “미래 이상을 위해 미리 올려둔 특별 이상 구간”이라기보다 config가 정의한 정상 baseline 수준으로 정확히 심긴 구간이다. 단차가 생긴 이유는 case-past가 비정상적으로 높아서가 아니라, 주변 순수 배경이 `BASELINE_RATE`보다 약 1/6 수준으로 희석되어 있기 때문이다.

### 가설 5. “baseline 희석을 고치면 헛알림률이 낮아질 것이다”

판정: 순감이 유력하지만, 재생성·재측정 전에는 확정할 수 없음.

이유:

탐지의 `MIN_DELTA`는 절대값 3%p다.

baseline 희석으로 인한 헛알림은 두 종류로 나눠야 한다.

- 순수 배경 노이즈성 헛알림: 배경 자체를 높이면 랜덤 fluctuation이 커져 일부 발화가 늘 수 있다.
- case-past 경계 단차성 헛알림: 주변 배경이 config baseline 수준으로 올라가면 `0.85% -> 5.03%` 같은 단차가 사라지므로 줄어들 가능성이 크다.

현재 남은 false 42건 중 40건은 어떤 형태로든 case-past overlap과 관련되어 있다. 따라서 현재 데이터에서는 baseline 희석을 고치면 헛알림이 줄어드는 순효과가 유력하다.

다만 이것은 아직 보정된 mock data를 실제로 재생성해 같은 평가 프로토콜로 다시 측정한 결과가 아니다. 그래서 최종 성능 개선으로 확정해 말하면 안 된다.

결론:

baseline 희석은 생성 정합성 문제로 고치는 것이 유력한 다음 작업이다. 단, “고치면 얼마로 좋아진다”는 수치는 재생성 후 독립 평가에서만 말해야 한다.

### 가설 6. “early_same_channel false 30건은 그냥 우연히 초반에 몰린 것이다”

판정: 단순 우연으로 보기 어렵다. 다만 독립 원인이라기보다 가설 4의 baseline 희석이 시간 경계에서 드러난 현상이다.

검증:

`early_same_channel` 30건을 따로 감사했다. 이 감사 대상은 day29-44에 걸쳐 있고, 그중 day29-32에 28건이 집중되어 있었다.

결과:

| 항목 | 값 |
|---|---:|
| 감사 대상 | 30 |
| 현재 7일 window가 generated case-past와 겹침 | 30/30 |
| 평균 overlap | 6.60일 |
| 평균 detector current rate | 7.93% |
| 평균 pre-case-past rate | 0.62% |
| 평균 generated case-past full rate | 5.32% |
| 평균 TRUE-window rate | 12.31% |

해석:

config상 TRUE case의 `past_neg` 구간은 `window_start_day - 28`일부터 시작한다. 이 구간은 config `past_rate`와 `BASELINE_RATE`에 맞게 생성되어 있다.

문제는 그 이전의 순수 배경이 config baseline보다 약 1/6로 희석되어 있다는 점이다. daily demo에서 case-past 시작 경계가 탐지기의 현재 7일 window에 들어오면, 탐지기는 `희석된 배경 -> config baseline 수준 case-past` 단차를 이상 상승으로 본다.

따라서 early false의 큰 원인은 “시간축 자체”라기보다, baseline 희석 때문에 case-past 시작일에 생긴 계통적 단차다.

### 가설 7. “TRUE가 없는 false 12건은 완전한 헛알림이다”

검증:

결과:

|---|---:|
| 미래 채점 제외 same PAS case-past | 6 |

12건 중 10건은 어떤 형태로든 config case-past와 현재 window가 겹쳤다.

따라서 TRUE가 없다고 해서 완전한 랜덤 헛알림으로 보면 안 된다.

### 가설 8. “마지막 미설명 2건은 분류기 문제다”

### 가설 9. “warmup/shadow를 쓰면 헛알림률이 낮아지므로 성능 개선으로 주장할 수 있다”

판정: 숫자상 낮아지는 것은 맞지만, 최종 성능 개선으로 주장하면 안 됨.

탐색 결과:

| 정책 | 케이스 도달 | True | False | 헛알림률 |
|---|---:|---:|---:|---:|
| Product x source baseline | 20/26 | 27 | 42 | 60.9% |
| Product x source warmup shadow d29-32 | 20/26 | 27 | 14 | 34.1% |

정정 기준의 세부값:

| 정책 | 발행 | 채점 | True | Ignored | False | 헛알림률 |
|---|---:|---:|---:|---:|---:|---:|
| Product x source baseline | 75 | 69 | 27 | 6 | 42 | 60.9% |
| Product x source warmup shadow d29-32 | 47 | 41 | 27 | 6 | 14 | 34.1% |

문제:

day 29-32에 false가 몰린 것을 본 뒤 만든 정책이므로, 같은 평가셋에서 좋아진 숫자를 최종 성능처럼 주장하면 평가셋 오버피팅이다.

결론:

warmup/shadow는 운영 정책 후보로 기록할 수는 있지만, 현재 실험의 성능 개선 결과로 쓰면 안 된다.

### 가설 10. “CS 색상 2-day gating이 좋은 해결책이다”

판정: 현재 기준으로는 우선순위가 낮음.

결과:

- `Product x source baseline`: 20/26 cases hit
- `Product x source + CS color 2-day`: 18/26 cases hit

헛알림은 줄 수 있지만 true alert와 케이스 도달률을 같이 깎는다.

또한 현재 주원인이 CS 색상 프롬프트가 아니라 baseline 희석으로 인한 case-past 경계 단차로 확인되었기 때문에, 이 정책을 먼저 적용하면 원인에 맞지 않는 처방이 된다.

## 7. 결과가 어떻게 바뀌었나

### 7.1 지표 변화

| 단계 | 발행 | 채점 대상 | True | Ignored | False | 헛알림률 | 케이스 도달 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 초기 raw | 75 | 75 | 27 | 0 | 48 | 64.0% | 20/26 |
| 채점 정정 후 | 75 | 69 | 27 | 6 | 42 | 60.9% | 20/26 |

주의:

발행 알림 수는 줄지 않았다. 셀러가 받는 알림은 여전히 75개다.

바뀐 것은 공식 채점에서 false로 세면 안 되는 6건을 `ignored`로 분리한 것이다.

### 7.2 원인 해석 변화

처음 의심:

- CS 색상 프롬프트 문제
- baseline이 낮게 깔려서 false가 많음
- threshold나 warmup으로 줄일 수 있음

검증 후 판단:

- CS 색상에 집중된 것은 맞지만, 프롬프트가 주원인은 아니다.
- baseline 희석은 맞고, 남은 false 대부분의 case-past 단차도 이 문제에서 나온 것으로 보인다.
- baseline 보정은 순감이 유력하지만, 공식 mock data 재생성 후 재측정하기 전에는 성능 개선 수치로 말하면 안 된다.
- threshold/warmup/gating은 지금 적용하면 평가셋 오버피팅 위험이 있다.
- 핵심 원인은 `BASELINE_RATE`를 전체 문의 분모로 볼 것인지 aspect 내부 비율로 볼 것인지가 생성기와 탐지 분모에서 어긋난 것이다.

## 8. 현재 남은 의사결정

기술적으로 다음 코드를 바로 고치기 전에 팀이 정해야 할 것이 있다.

### 선택지 A. case-past 조기 발화를 ignored로 뺀다

권장하지 않는다.

이 방식은 생성기 baseline 희석이라는 원인을 고치지 않고, 평가에서 증상만 가리는 방식이 될 수 있다. 특히 현재 false 분포를 본 뒤 만든 제외 규칙이므로, 연구 윤리 기준상 최종 성능 개선으로 쓰면 안 된다.

### 선택지 B. 생성기의 baseline 해석을 고친다

현재 기준에서 가장 원인에 맞는 선택지다.

팀이 `BASELINE_RATE`를 “전체 문의 중 해당 aspect 부정 비율”로 확정한다면, 생성기도 전체 문의 분모 기준으로 배경 부정률을 맞춰야 한다. 이 경우 순수 배경과 case-past baseline의 단차가 줄어들어 현재 false의 주된 원인이 사라질 가능성이 크다.

단, 공식 mock data 재생성과 성능 재측정은 별도 실험으로 기록해야 한다.

### 선택지 C. 조기 발화를 early warning으로 인정한다

현재 근거로는 성립하기 어렵다.

case-past는 config `past_rate = BASELINE_RATE`인 평상시 baseline 구간이다. 이상이 아닌 baseline 구간에서 뜬 알림을 조기 탐지 성공으로 부르면 안 된다.

## 9. 아직 하지 않은 일

아직 하지 않은 일:

- 공식 mock data 재생성
- `data/input`, `data/golden` 덮어쓰기
- threshold 변경
- prompt 변경
- warmup/shadow/gating 최종 채택
- 최종 성능 개선 주장

이것들은 팀 의사결정 후 별도 branch/실험에서 진행해야 한다.

## 10. 발표·보고에서 쓸 수 있는 표현

쓸 수 있는 표현:

> 실험 2 데모 결과의 초기 헛알림률은 64.0%였습니다. 성능을 임의로 튜닝하기 전에 false alert를 분해했고, 사전에 채점 제외로 정의된 window 6건이 false 분자에 들어간 것을 확인해 `ignored`로 분리했습니다. 그 결과 공식 채점 기준의 헛알림률은 60.9%로 정정되었습니다. 남은 false 42건 중 41건은 oracle/golden에서도 발생했기 때문에 분류기 문제가 아니라고 판단했습니다. 특히 `early_same_channel` 30건은 모두 case-past 구간과 현재 탐지 window가 겹쳤고, 추가 검산에서 이 case-past는 config baseline대로 생성된 반면 주변 순수 배경이 약 1/6로 희석되어 있음을 확인했습니다.

더 정확한 최신 표현:

> 추가 감사 결과, TRUE case-past 33행은 config `past_rate` 및 `BASELINE_RATE`와 33/33 일치했습니다. 따라서 case-past 자체가 비정상적으로 높은 것이 아니라, 일반 배경이 `BASELINE_RATE`보다 약 1/6 수준으로 희석되어 case-past 시작 경계에서 단차가 생긴 것으로 판단했습니다. 즉 높은 헛알림률의 핵심 원인은 프롬프트가 아니라 mock 생성기의 baseline 해석 문제입니다.

쓰면 안 되는 표현:

> 모델 성능을 개선해서 헛알림률을 64.0%에서 60.9%로 낮췄습니다.

왜 안 되는가:

60.9%는 성능 개선이 아니라 채점 정정 결과다.

또 쓰면 안 되는 표현:

> shadow warmup을 적용해서 헛알림률을 34.1%로 개선했습니다.

왜 안 되는가:

day 29-32에 false가 몰린 것을 본 뒤 만든 정책이므로, 같은 평가셋에서 좋아진 숫자를 최종 성능으로 주장하면 오버피팅이다.

## 11. 최종 권고

다음 순서로 가야 한다.

1. 팀과 `BASELINE_RATE`의 의미를 확정한다. 핵심 질문은 “전체 문의 분모인가, aspect 내부 비율인가”이다.
2. 전체 문의 분모가 맞다면 생성기의 배경 생성 로직을 보정한다.
3. 공식 mock data를 재생성할지, 별도 sandbox 데이터에서 먼저 검증할지 결정한다.
4. 보정된 데이터에서 실험 2 데모 성능을 다시 측정한다.
5. 그 뒤에도 헛알림률이 높으면 분류기 bias, threshold, persistence, gating을 별도 tuning set에서 검토한다.
6. 최종 성능은 tuning에 쓰지 않은 holdout에서 보고한다.

현재 단계에서 가장 정직한 결론:

> 실험 2의 높은 헛알림률은 모델 성능 문제라기보다 mock data 생성기의 baseline 해석 문제에서 비롯된 가능성이 크다. 순수 배경은 `BASELINE_RATE`보다 약 1/6로 희석되어 있고, case-past는 config baseline대로 생성되어 있어 그 경계에서 탐지가 발화한다. 따라서 지금은 모델을 튜닝할 때가 아니라, `BASELINE_RATE` 정의와 생성기 보정 여부를 먼저 확정해야 한다.
