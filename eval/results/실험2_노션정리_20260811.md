# 실험② 최종 결과 — Agent1 프롬프트 수정 전·후 이상탐지 성능 비교

## 1. 한 줄 결론

팀원 간 바이트 동일하게 재현된 canonical mock에서 Agent1 프롬프트 수정 전·후를 각각
독립 3회 측정한 결과, 이상탐지 recall은 **60.0%에서 82.7%로 +22.7%p 상승**했고
FPR은 양쪽 모두 0.0%였다.

이 결과는 같은 mock 개발셋에서 측정한 프롬프트 수정 효과이며, 외부 데이터에 대한
일반화 성능이나 통계적 유의성을 증명하는 결과는 아니다.

## 2. 전체 진행 과정

### 2-1. 발단 — 데모 성능이 지나치게 나빴다 (2026-08-06~07)

데모 시뮬레이션의 초기 결과는 다음과 같았다.

| 항목 | 초기 관측값 |
| --- | ---: |
| raw 헛알림률 | 64.0% (48/75) |
| 케이스 도달 | 20/26 |

처음에는 분류 프롬프트, `MIN_DELTA`·BH-FDR threshold, warmup/shadow 발행 정책을
의심했다. 그러나 false 42건을 분해하자 41건이 oracle/golden 분류에서도 발생했다.
즉 남은 문제의 대부분은 Agent1 분류기가 아니라 mock 데이터 또는 평가 구조에 있었다.

이 단계에서 성능이 나쁘다는 이유로 threshold를 낮추지 않았다. 같은 평가셋을 본 뒤 만든
warmup/shadow 규칙도 공식 성능 개선으로 채택하지 않고, 먼저 false의 발생 위치를
감사하는 방향으로 전환했다.

### 2-2. 채점 오류를 먼저 분리했다

초기 75개 알림 중 6개는 `scoring_included=N`이거나 `intended_answer`가 비어 있어
애초에 공식 채점에서 제외하도록 설계된 window였다. 이를 false가 아니라 `ignored`로
분리하면서 공식 헛알림률은 64.0%에서 60.9%(42/69)로 정정됐다.

이 변화는 모델이나 탐지기의 성능 개선이 아니다. **채점 규칙을 원래 설계대로 바로잡은
결과**다. 케이스 도달은 여전히 20/26이었다.

### 2-3. mock 생성기의 baseline 분모 결함을 찾았다

남은 false 중 가장 큰 덩어리는 `early_same_channel` 30건이었다. 30건 모두 미래 TRUE
케이스의 `case-past` 구간과 현재 7일 탐지 window가 겹쳤다.

| 감사 결과 | 값 |
| --- | ---: |
| case-past 평균 부정률 | 5.03% |
| 그 이전 순수 배경 평균 부정률 | 0.85% |
| 두 구간 비율 | 6.04배 |

case-past가 과도하게 높았던 것이 아니라, 그 전의 순수 배경이 지나치게 낮았다.
`generate_cs_review_data.py`를 확인한 결과 두 생성 경로가 서로 다른 분모를 쓰고 있었다.

```text
케이스 경로
  past_neg / cur_neg를 상품·채널 전체 문의 분모에 정확 건수로 심음

배경 경로
  먼저 문의량을 aspect 수로 나눈 뒤 BASELINE_RATE를 적용
```

확정 스펙은 `(상품, 채널, source)`의 전체 문의가 분모다. 그런데 배경 경로는 aspect 내부
분모를 사용해 전체 문의 기준으로 CS는 약 1/6, 리뷰는 약 1/3로 희석됐다. 이는 정의 선택의
문제가 아니라 이미 정해진 스펙을 어긴 생성기 결함이었다.

`38c1074`에서 배경 생성에 `--baseline-denominator total`을 추가하고 전체 문의 분모로
통일했다.

### 2-4. 첫 mock 재생성과 검산 (2026-08-09)

`data/**`는 git에 올라가지 않는 로컬 파일이라 덮어쓰기 전에 기존 `data/input`,
`data/golden`, `data/config`를 아카이브했다. 원인 문장은 LLM 출력이라 seed만으로 재현할
수 없으므로 저장소 루트의 `cause_text_cache.json`도 함께 보존해야 했다.

재생성 조건은 다음과 같았다.

```text
anchor-date = 2026-08-28
seed = 11
baseline-denominator = total
cause_text_cache = 14개 키 전체 적중, 신규 LLM 호출 0회
```

재생성 직후 검산 결과:

| 항목 | 결과 |
| --- | --- |
| CS / 리뷰 행수 | 96,524 / 31,639 |
| golden 부정 문서 | 23,950 |
| `verify_counts.py` | 246 슬롯 PASS / FAIL 0 |
| 실험① oracle | 25/25 recall · 0/8 FPR · 33/33 verdict |
| 데모 oracle 케이스 도달 | 20/26 → 26/26 |
| 데모 oracle 헛알림률 | 15.6% |

행수는 96,531에서 96,524로 바뀌었지만 케이스 슬롯 카운트는 config와 그대로
일치했다. 이 시점부터 `data/input`·`data/golden`을 읽는 재생성 이전 실험 수치는
재측정 대상으로 분류했다. 재생성 전 실험② 48.0%/60.0%, 실험③의 옛 mock F1 등은
최종 근거에서 제외했다.

### 2-5. 재생성 과정에서 평가 도구의 조용한 오염 경로를 고쳤다

재생성만 하고 기존 평가 코드를 그대로 실행하면 새 데이터에 옛 결과가 섞일 수 있었다.
다음 경로를 순서대로 수정했다.

1. **캐시에 데이터 지문 추가 — `6acca6b`**
   - 기존 캐시는 프롬프트 지문과 `item_id`만 봤다.
   - 재생성 후 같은 ID에 다른 문장이 붙어도 옛 분류를 신규 호출 0건으로 재사용할 수
     있었다.
   - 현재 window의 `(id, text)`를 해싱한 `data_fingerprint`를 캐시 파일명에 추가했다.
2. **데모의 조용한 oracle 폴백 차단 — `6acca6b`**
   - real 캐시에 없는 문서를 golden으로 되돌리던 경로를 막았다.
   - 캐시 적용률이 99% 미만이면 real 결과를 공식 출력하지 않게 했다.
3. **실험②에 리뷰 포함 — `c3e00d9`**
   - 채점 33건 중 리뷰 2건이 실제 분류가 아니라 oracle로 남아 있던 문제를 고쳤다.
   - 현재 측정 대상은 CS 11,990 + 리뷰 420 = 12,410건이다.
4. **오차 진단 범위를 config 슬롯으로 제한 — `641ef8d` 계열**
   - 전체 12,410건 기준 0.75%라는 설명은 채점에 닿지 않는 문서가 62% 섞인 값이었다.
   - 실제 config 슬롯에서는 약 1,278건 중 80건, 약 6.2%였다.

### 2-6. Agent1 프롬프트의 명세 모순을 고쳤다 (2026-08-10)

오차 문장 유형을 분해하자 “게시 정보와 실제 상품의 차이”를 다루는 규칙이 프롬프트
안에서 서로 충돌했다. 같은 형태의 문장이 한 규칙에서는 부정, 다른 규칙에서는 중립이 될
수 있었다.

첫 수정안은 “게시 정보의 정확성을 문제 삼는가”를 기준으로 삼았지만 회귀 평가에서 FPR이
0.0%에서 1.8%로 올랐다. 오탐 5건이 같은 문장 유형에서 나온 것을 확인하고 이 초안은
채택하지 않았다.

최종 수정은 화자의 주관적 판단이 아니라 문장에 게시 정보 언급과 불일치 주장이 실제로
있는지를 기준으로 정리했다. 관련 변경은 `7c694f6`, `25f4966`, `a59233c`에 누적됐고,
aspect 프롬프트 내용 지문은 다음과 같이 바뀌었다.

| 구분 | 지문 |
| --- | --- |
| before | `classify_aspect_v5-2d7e1839` (`93b8ee4` 내용) |
| after | `classify_aspect_v5-af48384c` |

### 2-7. 반복 측정의 독립성 결함을 고치고 첫 after를 다시 돌렸다

초기 평가기는 한 회차에서 응답이 누락된 문서를 다음 회차 실행 때 같은 캐시에 채웠다.
그 결과 회차별 시도 횟수와 커버리지가 달랐다.

```text
회차 1: 뒤 실행에서 여러 번 보충
회차 2: 뒤 실행에서 한 번 보충
회차 3: 최초 호출만 수행
```

실제로 회차 1은 `--runs 1`일 때 60.0%(7슬롯 제외)였지만, 같은 캐시로 `--runs 2`를
실행하자 47건이 채워져 84.0%로 바뀌었다. 이 상태의 반복값과 `84.0% ±0.0%`는 독립
시행이 아니므로 폐기했다.

`38b71a3`과 `0f3e76e`에서 `RETRY_WITHIN_RUN = 2`를 도입했다. 누락 문서는 캐시에
넣지 않고 **같은 회차 안에서만** 최대 두 번 재시도하도록 batch와 per_item 경로를 모두
고쳤다. 재시도 예산과 캐시 미기록 동작은 `tests/test_run_within_retry.py`로 고정했다.

이 코드로 당시 재생성 데이터 `d1fb05ed9`의 after를 빈 캐시에서 다시 측정한 결과는
80.0% / 84.0% / 72.0%, 평균 78.7%였다. 세 회차 모두 최종 무응답과 제외 슬롯이 0이라
이전의 `84.0% ±0.0%`를 대체했다. 다만 before 56.0%는 옛 방식으로 완성된 캐시라
독립 시행 점추정으로만 남았다.

### 2-8. 재생성 레시피의 cause 텍스트 오염 경로를 막았다

팀원이 같은 데이터를 재생성하는 과정에서 두 가지 문제가 추가로 발견됐다.

1. 생성기의 기본 cause 프롬프트 경로는 `prompts/generate_cause_text_v3.md`였지만 실제
   파일은 `scripts/prompts/generate_cause_text_v3.md`에 있었다.
2. 파일을 못 찾았을 때 생성기가 멈추지 않고 아래 형태의 플레이스홀더를 만들었다.

```text
[PLACEHOLDER:cause:색상:사진*색감*오차]
```

이 문자열은 원인 정답을 본문에 노출하므로, 그대로 실험⑥을 채점하면 모델이 문장을
분류하는 것이 아니라 답을 복사하게 된다. 캐시가 이미 100% 있는 사람은 프롬프트 파일을
읽지 않아 이 결함을 밟지 않았고, 행수 검산도 통과해 사람마다 조용히 다른 결과를 만들 수
있었다.

또한 `cause_text_cache.json`은 저장소 루트의 gitignore 대상이라 `data/`만 아카이브하면
빠졌다. 덮어쓰면 같은 seed로 복구할 수 없는 LLM 출력이 사라지는 문제도 있었다.

다음과 같이 수정했다.

- `3cf8182`: 기본 경로를 스크립트 기준 절대경로로 바꾸고, 파일이 없으면 즉시 중단
- `6eef993`: 캐시 hit·신규 저장·최종 CSV 세 단계에서 플레이스홀더를 거부하고, LLM
  초기화 실패나 4라운드 부족을 정상 데이터처럼 저장하지 않음
- `e2808c3`: 한국어 Windows cp949 콘솔에서도 중단 사유가 traceback에 묻히지 않도록
  생성기 진입점의 UTF-8 출력 배선과 회귀 테스트 추가
- 재생성 아카이브 레시피에 저장소 루트의 `cause_text_cache.json` 포함

최종 실험에 사용한 cause 캐시는 팀원 파일과 JSON 내용 기준 14개 키·280문장이 같았고,
네 CSV도 바이트 동일했다. 따라서 최종 데이터 차이의 원인은 cause 캐시가 아니었다.

### 2-9. 같은 seed인데도 달라지는 생성기 비결정성을 고쳤다

생성기 안의 `group_aspects`가 `set`이었다. Python 문자열 set의 순회 순서는 프로세스의
`PYTHONHASHSEED`에 따라 달라지므로, 같은 코드·config·templates·seed·cause cache를
사용해도 색상/파손 중 어느 aspect가 하루치 부정 슬롯을 먼저 가져가는지가 바뀌었다.

이 결함은 특히 찾기 어려웠다.

- 행수, ID, 날짜, 채널, sentiment 수는 같았다.
- aspect별 `past_neg`·`cur_neg` 집계도 같았다.
- `verify_counts.py` 246 슬롯도 모두 통과했다.
- 달라지는 것은 특정 ID에 어떤 aspect 문장이 붙는지였다.

실측에서 팀원 코퍼스가 `1fb05ed9`와 `07276bc5`로 갈렸고 리뷰 CSV는 같지만 다중-aspect
그룹이 있는 CS CSV가 달랐다. `fea4329`에서 `set`을 `dict.fromkeys`로 바꿔 config의 첫
등장 순서를 보존했고, 별도 프로세스의 여러 `PYTHONHASHSEED`에서도 결과가 같아지는
테스트를 추가했다.

이 경험 때문에 최종 재현 확인은 `data_fingerprint` 하나에만 의존하지 않았다.
`data_fingerprint`는 실험② 현재 window만 덮으므로, 전체 코퍼스는 네 CSV의 SHA-256과
`verify_counts`를 함께 비교했다.

### 2-10. PR #54 머지 후 canonical 재생성과 최종 재측정 (2026-08-11)

PR #54가 머지된 `main`의 `4c66e72`에서 팀원과 각각 mock을 다시 생성했다. 양쪽 모두
다음 값이 일치했다.

- CS / 리뷰 행수: 96,524 / 31,639
- `verify_counts.py`: 246 PASS / 0 FAIL
- `data_fingerprint`: `07276bc5`
- 네 CSV SHA-256: 모두 일치
- cause 캐시: 14개 키·280문장 동일

유료 호출 전에 로컬 루트 데이터의 지문도 다시 확인했다. 로컬에는 이전 데이터
`76b878a6`이 남아 있어 실행을 중지하고 기존 파일을 별도 백업한 뒤, 앞에서 SHA-256을
검증한 canonical 네 CSV로 교체했다. 교체 후 `2d7e1839 + d07276bc5`, 문서 12,410건,
관련 캐시 0개를 확인했다.

첫 before 실행은 기존 API 키의 10 RPM / 60k TPM 제한으로 429가 반복됐다. 이 상태로
계속하면 회차가 깨끗하게 닫히지 않으므로 160건에서 중단했고, 부분 run1 캐시를 격리한
뒤 프롬프트를 current after로 원복했다. 이 중단 실행은 최종 결과에 포함하지 않았다.

API 키를 교체한 뒤 다시 빈 캐시에서 전체 과정을 실행했다.

1. `93b8ee4`의 before 프롬프트 적용
2. `2d7e1839 + d07276bc5`, 활성 캐시 0 확인
3. before 3회 실행
4. current after 프롬프트로 원복하고 Git diff가 비었는지 확인
5. `af48384c + d07276bc5`, 활성 캐시 0 확인
6. after 3회 실행

최종 결과는 before 60.0% / 60.0% / 60.0%, after 84.0% / 76.0% / 88.0%였다.
여섯 회차 모두 12,410/12,410, 최종 무응답 0, 제외 슬롯 0으로 종료됐다. 마지막에는
프롬프트가 current after `af48384c`로 원복된 것도 확인했다.

따라서 현재 정본은 `d07276bc5`의 before **60.0%**, after **82.7%**, 관측 개선 폭
**+22.7%p**다.

## 3. 무엇을 측정했나

멀티에이전트 CS 분석 파이프라인에서 Agent1의 분류 오차가 Agent2 이상탐지 성능에
미치는 영향을 측정했다.

```text
CS 문의·리뷰 원문
  → Agent1: aspect + sentiment 분류
  → Agent2: Fisher 단측검정 + BH-FDR(q=0.05) + 최소 절대차 3%p
  → 편중형·전역형 판정
```

- 실험① oracle: Agent1 대신 golden label을 입력해 구현과 설계 의도의 일치를 검산한다.
- 실험② before: 수정 전 aspect 프롬프트를 사용한다.
- 실험② after: 현재 aspect 프롬프트를 사용한다.
- before와 after의 차이가 동일 조건에서 관측된 프롬프트 수정 효과다.

## 9. 해석 시 반드시 붙여야 할 한계

1. **일반화 성능이 아니다.** 결함을 찾고 프롬프트를 수정한 mock 개발셋과 성능을 측정한
   데이터가 같다. 고유 문장 종류도 제한적이라 행 단위 분할로 홀드아웃을 만들 수 없다.
2. **통계적 유의성을 검정하지 않았다.** +22.7%p는 동일 조건의 관측 차이다.
3. **n=3이다.** before 세 회차가 모두 60.0%였어도 일반적인 안정성을 증명하지 않는다.
4. **FPR 0%를 안전성 근거로 쓰지 않는다.** 분모가 정상 케이스 8개뿐이다.
5. **oracle 100%는 모델 성능이 아니다.** 설계 의도와 구현이 일치하는지 보는 검산이다.
6. **운영과 호출 방식이 다르다.** 비용 때문에 CS는 batch로 측정했다. batch와 운영의
   per_item 동등성은 실험③ 결과에 근거한 가정이다.
7. **mock 문장 다양성이 작다.** 실제 고객 문의의 표현 분포를 대표하지 않는다.
