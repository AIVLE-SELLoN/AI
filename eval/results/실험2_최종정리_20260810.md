## 0. 한 줄 요약

**두 개의 서로 다른 결함을 각각 고쳤다.** 원인도 효과도 분리해서 읽어야 한다.

| 고친 것 | 효과 | 무엇으로 확인했나 |
| --- | --- | --- |
| **① mock data 생성기** — 배경 부정률이 설계값의 1/6 | 데모 **케이스 도달 20/26 → 26/26** | 데모 oracle (골든 라벨, LLM 0회) |
| **② 프롬프트1 명세 모순 + 측정 조건 정정** | 실험② **탐지율 56.0% → 78.7%** | 실험② (실제 분류, 회차 독립 3회) |

> 🔴 **①이 ②를 만든 게 아니다.** 실험②의 before(56.0%)·after(78.7%)는 **둘 다 재생성된 데이터**에서 잰 값이고, 차이는 프롬프트1 수정과 측정 조건 정정에서 온다.
> 생성기 수정의 효과는 데모 케이스 도달률(20/26 → 26/26)에서 보이고, 실험②의 탐지율 변화와는 별개다.

그리고 이 과정에서 평가 도구가 **틀린 숫자를 조용히 내던 경로 다섯 개**를 같이 막았다.

## 1. 최종 성능

| 측정 | 값 | 조건 |
| --- | ---: | --- |
| **데모 — 헛알림률** | **15.6%** | oracle · 상품별 family · 32일 |
| **데모 — 케이스 도달** | **26/26** | 이전 20/26 |
| **실험② — 탐지율** | **78.7%** (관측 폭 72~84%) | **동일 mock 개발셋** · 실제 분류 · 회차 독립 3회(80.0/84.0/72.0) · 이전 56.0% |
| **실험② — 오탐률** | **0.0%** (3회 모두 0/8) | 변화 없음 |

> 🔴 **`±` 를 표준편차나 신뢰구간으로 읽지 마라.** 스크립트가 찍는 `±` 는
> **반범위** `(max−min)/2` 다(`run_pipeline_eval.py` `report()`). n=3 반범위는 양 끝 두
> 점만 쓰고 가운데를 버리는 가장 거친 산포 측도이고, 범위는 표본이 커질수록 넓어지므로
> **구조적으로 과소추정**이다. 4회차가 72~84% 밖으로 나오는 건 이상한 일이 아니다.
>
> 그래서 이 문서는 `78.7% ±6.0%` 대신 **"3회 평균 78.7%, 관측된 폭 12%p(72~84%)"** 로
> 적는다. 이건 흔들림의 **하한 감각**을 줄 뿐 구간 추정이 아니다.
| 실험① — 전 지표 | 100% | oracle · 25/25 · 0/8 · 33/33 |

> ⚠️ **각 숫자가 답하는 질문이 다르다.**
> 실험① = 구현이 스펙대로 동작하는가(성능 아님) · 데모 = 셀러가 받는 알림(단 oracle) · 실험② = 분류 오차가 탐지를 얼마나 깎는가.
> **어느 하나도 단독으로 "서비스 성능"이 아니다.**

## 2. 발단 — 헛알림률이 높은데 원인을 모름

데모 시뮬레이션에서 헛알림률이 높게 나왔다. 처음 의심은 셋이었다.

1. CS 색상 프롬프트가 문제다
2. threshold(`MIN_DELTA`·`BH_FDR_Q`)를 완화하면 된다
3. warmup/shadow 같은 발행 정책으로 줄인다

**셋 다 틀렸거나 부적절했다.**

- 남은 false 42건 중 **41건이 oracle(정답 라벨)에서도 발생** → 분류기 문제가 아님
- threshold 완화는 채점셋에 맞춰 임계를 돌리는 오버피팅
- warmup/shadow는 day29–32에 false가 몰린 것을 **본 뒤에** 만든 규칙 → 같은 평가셋 성능으로 주장 불가

그래서 방향을 "성능을 올린다"에서 **"왜 이런 숫자가 나오는지 분해한다"** 로 바꿨다.

### 결정적 단서

`early_same_channel` false 30건을 감사했더니 **30/30 전부** 미래 TRUE 케이스의 `case-past` 구간과 현재 7일 윈도우가 겹쳤다.

| 항목 | 값 |
| --- | ---: |
| 평균 overlap | 6.60일 |
| 평균 탐지기 현재 부정률 | 7.93% |
| 평균 case-past 이전 배경 | 0.62% |
| 평균 case-past 구간 | 5.32% |

**case-past가 비정상적으로 높은 게 아니라, 그 앞의 배경이 비정상적으로 낮았다.**

## 3. 진짜 원인 — 생성기가 `BASELINE_RATE`를 두 가지로 해석하고 있었다

### 3-1. 무엇이 어긋났나

`scripts/generate_cs_review_data.py` 안에 **규약이 두 개** 있었다.

```
케이스 경로   build_rows_for_window_group
              past_neg / cur_neg 를 전체 분모에 정확 건수로 심음        ✅ 스펙대로

배경 경로     build_rows_for_product_background
              볼륨을 aspect 수로 먼저 나눈 뒤 그 안에서 확률 적용       ❌ 희석
              per_aspect_daily = volume / len(aspects)
```

전체 문의 분모로 보면 **CS는 1/6, 리뷰는 1/3로 희석**된다.

### 3-2. 물증

| 확인 항목 | 결과 |
| --- | ---: |
| TRUE config 33행의 `past_rate == BASELINE_RATE` | **33/33 일치** |
| 평균 case-past 관측률 | 5.03% |
| 평균 순수 배경 관측률 | **0.85%** |
| 비율 | **6.04배** (= CS aspect 수 6) |

케이스는 설계대로 심겼는데 배경만 1/6이었다. 그 경계에서 탐지기가 "이상 상승"으로 읽었다.

### 3-3. 이건 정의 선택이 아니라 스펙 위반이었다

전체 문의 분모(aspect 무관)라는 근거가 **세 곳**에 이미 있었다.

1. **이상탐지 시나리오 정의서 §1** — 최소표본 항목에 "(상품,채널) 총문의(= 분모, aspect 무관)"
2. **`config_anomaly.csv`** — SC-001 쿠팡 색상 `past_neg=40 / past_total=800`. 800 = 28일 × 28건 = CS 전체 볼륨
3. **`app/detection/aggregate.py`** — 탐지 분모도 (상품, 채널, source) 총문의

> 초기 문서는 이걸 "팀이 정의를 확정할 문제"로 올렸다. **잘못된 프레이밍이었다.**
> 팀 리뷰에서 "합의 사항이 아니라 구현이 확정 스펙을 어긴 결함"으로 정정했고, 그에 따라 회의 안건이 아니라 defect 처리로 갔다.

### 4-1. 사전 조건

1. **옛 데이터 아카이브** — `data/**` 가 전부 미커밋이라 덮어쓰면 복구 불가

## 5. 그 과정에서 발견한 측정 도구 결함 5개

재생성만으로 끝나지 않았다. 평가 도구가 **틀린 숫자를 조용히 내는 경로**가 여러 개 있었다.

### ① 캐시가 데이터 변경을 못 잡았다 — `#49`

분류 캐시가 `item_id` 로만 조회하는데, mock 을 재생성하면 **같은 ID에 다른 텍스트**가 들어간다. 파일명이 `pipeline_{tag}_{mode}_{프롬프트지문}_run{n}` 이라 데이터 지문이 없었다.

→ 재생성 후 그대로 돌리면 **"신규 호출 0건"으로 조용히 통과하면서 옛 라벨로 새 문서를 채점**한다. 비용이 안 드는 것처럼 보이면서 결과만 틀린다.

같은 파일의 `prompt_fingerprint` 주석이 프롬프트에 대해 이미 이 논리를 써놨는데(내용 해시로 제자리 수정까지 잡는다) 데이터로 확장이 안 돼 있었다. `data_fingerprint()` 를 추가했다.

> 실제로 이 지문이 작동했다. 브랜치를 잘못 체크아웃해 옛 프롬프트로 3회를 돌렸을 때, 지문이 갈려 별도 캐시로 가면서 즉시 알아챘다.

### ② 데모가 "real인 척하는 oracle"을 낼 수 있었다 — `#49`

`demo_sim.swap_real()` 은 캐시에 없는 `item_id` 를 **조용히 golden 으로 되돌린다.** 캐시 경로도 하드코딩이라 새 캐시를 만들어도 못 찾았다.

| | 건수 |
| --- | ---: |
| 데모가 보는 문서 | 128,163 |
| 실험②가 만드는 캐시 | 12,410 |
| **적용률** | **9.7%** |

→ 그대로 두면 9할이 oracle 인 값이 "real" 로 찍힌다. 파일명 하드코딩을 **적용률 기반 선택**으로 바꾸고, 99% 미만이면 `real` 팔을 아예 빼도록 했다.

### ③ 실험②가 리뷰를 빼고 재고 있었다 — `#49`

채점 단위 33건 중 리뷰가 2건(SC-034/review, SC-035/review)인데, `collect_documents` 가 `source != cs` 를 건너뛰어 **그 2건이 oracle 인 채로 점수에 들어갔다.**

문서 어디에도 근거가 없었다. 헤더의 "왜 케이스만 실제 분류하나"는 **배경 슬롯** 제외 근거이고(합성값이라 원문이 없다), 그 논리는 리뷰에 적용되지 않는다 — `input_reviews.csv` 에 원문이 실재한다.

리뷰 420건을 프롬프트2 `per_item` 으로 태워 **33건 전부 실제 분류로 측정**하게 고쳤다.
(배치 조립기가 프롬프트1 전용이라 리뷰는 `per_item` 이어야 한다)

### ④ 오차 분해의 분모가 62% 희석돼 있었다 — `#49`

재생성으로 케이스 윈도우의 골든 부정이 1,618 → 3,367 로 늘었는데, **채점에 닿는 config 슬롯 몫은 1,278 로 그대로**였다. 슬롯 내 비율이 79% → **38%** 로 떨어졌다.

`measure()` 는 config 슬롯만 내고 나머지는 합성값을 쓰므로, 슬롯 밖 문서의 분류 결과는 **분자에도 분모에도 안 닿는다.**

| | 전체 | config 슬롯 내 |
| --- | ---: | ---: |
| 정답 (부정 유지) | 9,754 (96.6%) | 3,558 (**92.8%**) |
| 감성만 뒤집힘 | 280 (2.8%) | 239 (**6.2%**) |
| 합계 | 10,101 | 3,834 (38%) |

주장이 이렇게 바뀌었다.

- 이전: "12,410건 중 93건(**0.75%**)이 44%p를 만든다"
- 정정: "1,278건 중 약 80건(**6.2%**)이 44%p를 만든다"

### ⑤ 반복 측정이 독립이 아니었다 — `fix/run-independence`

**가장 크게 숫자를 흔든 결함.** 무응답 건을 **다음 회차 실행으로 미루고** 있었다.

```
회차 1   1차 + (2회 실행 재호출) + (3회 실행 재호출)   ← 시도 3번
회차 2   1차 + (3회 실행 재호출)                       ← 시도 2번
회차 3   1차만                                          ← 시도 1번
```

회차는 LLM 흔들림을 평균 내려고 나눈 것이라 **서로 독립이어야 하는데**, 앞 회차일수록 커버리지가 좋아졌다.

실측으로 드러났다.

| 실행 | 회차 1 값 |
| --- | ---: |
| `--runs 1` | 60.0% (7슬롯 제외) |
| `--runs 2` | **84.0%** (47건이 채워짐) |

모델이 달라진 게 아니라 **채점 대상이 달라졌다.**

| 조건 | 탐지율 |
| --- | ---: |
| 스크립트 기본 출력 (커버리지 비대칭) | 78.7% ±8.0% |
| 채점 조건 통일 | 68.0% ±4.0% |
| 커버리지 완전 충전 (수작업) | 84.0% ±0.0% |

당시에는 여기서 **"편차가 전부 커버리지 비대칭이고 LLM 흔들림은 사실상 0"** 이라고 적었다.
**이 결론은 틀렸다.** 아래 재실행이 뒤집는다.

### 5-3. 고치고 다시 쟀다 — 여기가 정본이다

`RETRY_WITHIN_RUN = 2` 로 **회차 안에서** 재시도하게 고친 뒤(`0f3e76e`), 배치·per_item
양쪽 경로에 다 적용하고, **빈 캐시에서 `--runs 3` 을 딱 한 번** 실행했다.

```
지문   classify_aspect_v5-af48384c_classify_sentiment_v4-ef7a6c8d-d1fb05ed9

```

| 회차 | 최초 대상 | 회차 내 재시도 | 최종 무응답 | 제외 슬롯 | 탐지율 |
| --- | --- | --- | --- | --- | ---: |
| 1 | 12,410 (캐시 0) | 33건 (1/2) | **0** | **0** | 80.0% |
| 2 | 12,410 (캐시 0) | 43건 (1/2) | **0** | **0** | 84.0% |
| 3 | 12,410 (캐시 0) | 7건 (1/2) | **0** | **0** | 72.0% |

**세 회차의 채점 대상이 완전히 같다.** 그런데도 값은 72~84% 로 벌어진다.

| | 이전 결론 | 재실행 결과 |
| --- | --- | --- |
| 탐지율 | 84.0% (3회 모두 동일) | **78.7%** (72 / 80 / 84) |
| 회차 간 차이의 정체 | "커버리지 비대칭이 전부" | **LLM 흔들림** |

**결론이 ± 의 크기에 걸려 있는 게 아니다.** "이전 ±0.0% 는 안정이 아니라 흔들림이 가려진
상태였다"는 **회차마다 채점 대상이 달랐다는 사실**로 증명된다(회차 1 이 `--runs 1` 에서
7슬롯 제외 60.0%, `--runs 2` 에서 84.0%). 산포 측도가 무엇이든 이 논지는 그대로다.

**±0.0%(세 회차가 전부 같은 값)는 안정성이 아니라 흔들림이 가려진 상태였다.** 회차별 커버리지를 사람이 맞춰
놓으면 회차 간 차이가 사라진 것처럼 보인다. 그리고 84.0% 는 이번 3회 중 **2회차 값**이다 —
운 좋은 회차를 대표값으로 쓰고 있었던 셈이다.

> ⚠️ 위 표의 "스크립트 기본 출력 78.7% ±8.0%" 와 재실행의 78.7% 는 **우연히 평균이
> 같을 뿐 다른 것**이다. 앞은 커버리지가 비대칭인 상태의 값이고, 뒤는 대칭인 상태의 값이다.

## 6. 프롬프트1 명세 모순 정리 (Agent1)

### 6-1. 무엇이 모순이었나

오차 분해에서 뒤집힌 문장이 **83종**으로 특정됐고, 원인이 프롬프트 안의 규칙 충돌이었다.

```
예시 15-1 · 15-3 · 20-2    게시물 ↔ 실물 대조 → -1
예시 29                    게시물 ↔ 실물 대조 →  0    ← 같은 문장이 양쪽에 해당
```

**같은 모양의 문장이 두 규칙에 동시에 걸려 라벨이 임의가 됐다.**

### 6-2. 초안이 틀렸고, 되돌렸다

첫 수정안은 갈림길을 **"게시 정보의 정확성을 문제 삼는가"** 로 잡았는데, 회귀 가드에서 **FPR 0.0% → 1.8%** 로 올랐다. 오탐 5건을 특정하니 **전부 같은 문장 1종**이었다.

골든과 대조한 결과 진짜 갈림길은 **"다르다고 말했는가"** 였고, 최종적으로 **"게시물 얘기를 꺼냈는지"** 로 정리됐다. 화자의 주관 판단이 아니라 **문장에 무엇이 있는지**로 옮긴 것이라 재현성이 올라갔다.

### 6-3. 결과 (`relabel_300` 기준 — 이 PR에서 안 건드린 평가셋)

> ⚠️ **이 표의 숫자를 실험②의 78.7% 와 같은 줄에 놓지 마라. 다른 평가셋이다.**

## 8. 한계 — 발표에서 먼저 밝혀야 할 것

### 8-1. 데모 `real` 은 못 쟀다

셀러가 실제로 받는 헛알림률을 32일 시뮬레이션으로 직접 재려면 **전량 128,163건 분류 캐시**가 필요하다.

| 방식 | 비용 | 문제 |
| --- | ---: | --- |
| 배치 | ~$10 | 운영은 건당이라 "동등성은 가정" 단서가 붙는다 |
| 건당 (운영과 동일) | ~$120 | 예산 대비 과함 |

또 `swap_real` 이 캐시 미스를 golden 으로 폴백하므로, 돌리기 전에 그것도 운영처럼 `기타/중립` 으로 바꿔야 진짜 운영 재현이 된다.

**"안 쟀다"가 아니라 "재는 비용과 그 값의 한계를 알고 제외했다"** 가 정확한 서술이다.

### 8-2. 오탐률 0%를 안전성 근거로 쓸 수 없다

- 분모가 **8** (설계상 정상인 케이스 슬롯)
- ②는 현재 윈도우만 실제 분류로 갈고 과거·배경은 oracle 이라, 오차가 **"이상 없음" 방향으로만 민다**
- 역방향 오판(비부정 → 부정)을 재보니 리뷰가 회차당 21건인데 **고유 1종**이었다. 리뷰 비부정 모집단이 **15종**뿐이라 문서당 오판률이 아니라 템플릿 하나의 문제다

**FPR 0/8 은 표본 크기 문제도 아니고 리뷰 문장이 15종뿐인 데이터의 결과다. 운영 FPR 에 대해 ②는 아무 말도 못 한다.**

### 8-3. mock 데이터의 표본 한계

| | 행수 | 고유 문장 |
| --- | ---: | ---: |
| CS | 96,524 | **329종** |
| 리뷰 | 31,639 | **30종** |

- 홀드아웃을 행 분할로 못 만든다 — 어떻게 쪼개도 같은 문장이 양쪽에 들어간다
- **프롬프트2는 이 데이터로 고치면 안 된다** — 리뷰 15종 중 1종 맞히기가 된다. 실험④(AI Hub 71603)로 가야 한다

> 🔴 **78.7% 는 "동일 mock 개발셋" 결과다.** 생성기 결함을 찾고 프롬프트1을 고칠 때 본
> 데이터와, 최종 성능을 잰 데이터가 같다. 홀드아웃이 아니므로 **일반화 성능이 아니라
> 개발셋 성능**이고, 실제 CS/리뷰에서 이만큼 나온다는 근거가 되지 못한다.
>
> 위 표대로 고유 문장이 CS 329종·리뷰 30종뿐이라 행을 나눠도 홀드아웃이 안 만들어진다.
> 외부 데이터 기준 값이 필요하면 실험④(AI Hub)와 `relabel_300`(§6-3)을 봐야 한다.

### 8-4. 배치 ↔ 건당 동등성은 측정이 아니라 가정

평가는 비용 때문에 배치(청크 20건), 운영은 건당이다. 동등성 근거는 실험③ 비교인데, 대표 지표가 바뀐 뒤로 **새 지표 기준 재검증이 안 됐다.** 리포트가 매 실행 이 문구를 출력한다.

### 8-5. 배치 응답 누락을 회차 안에서 재호출했다

배치 응답에서 `item_id` 가 빠지는 경우가 있다. 최종 3회 실행 기준 **회차당 33 / 43 / 7건**
(11,990건 대비 0.28% / 0.36% / 0.06%)이었고, 전부 재시도 1회로 채워져 최종 무응답 0 이다.

**응답이 없는 건만** 같은 회차 안에서 다시 불렀고 내용을 보고 고르지 않았다. 예산은
`RETRY_WITHIN_RUN = 2` 로 상한이 박혀 있어 "될 때까지" 돌리지 않는다.

운영은 건당 호출이라 이 누락이 발생하지 않으므로 **평가 전용 아티팩트**로 보고 제거했다.
→ 만약 운영도 배치로 간다면 이 논리가 무너진다. 그땐 0.4%가 실제 손실이다.

### 8-6. AI Hub 원문이 히스토리에 남아 있다

`relabel_300.csv`(299행) 와 `hybrid_verify_20260806_144446.json`(133건)을 작업 트리에서 제거하고 `.gitignore` 로 막았다(#45). 사람이 한 재라벨링 300건은 원문 없이 `relabel_300_labels.csv` 로 보존했다.

다만 **히스토리(`0be8a32`)에는 그대로 남아 커밋 SHA 로 조회된다.** 완전히 닫으려면 커밋 53개 재작성 + 브랜치 9개 force-push + `refs/pull/*` 정리(GitHub Support)가 필요하고, 300행 리뷰 텍스트(개인정보 0건) 대비 비용이 과해 발표 후로 미뤘다.

## 12. 이번 작업의 성격

- 평가 도구가 조용히 틀린 값을 내던 경로 다섯 개를 기계가 막게 했다(사람이 기억하는 규칙이 아니라)
- 틀린 결론 여섯 개를 스스로 찾아 철회했다
