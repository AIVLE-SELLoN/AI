# 실험 2 성능 개선·정정 작업 정리, 2026-08-07

## 한 줄 결론

현재까지 한 작업은 “모델 성능을 실제로 개선했다”기보다, 실험 2 데모 평가에서 헛알림률이 높게 나온 원인을 분해하고 채점 기준 오류를 바로잡은 것이다.

정직하게 말할 수 있는 최신 지표는 다음과 같다.

| 지표 | 값 |
|---|---:|
| family | product x source |
| label | real classification |
| 발행 알림 | 75 |
| 채점 대상 알림 | 69 |
| true 알림 | 27 |
| ignored 알림 | 6 |
| false 알림 | 42 |
| 헛알림률 | 60.9% |
| 케이스 도달률 | 20/26 |

`60.9%`는 성능 개선값이 아니라 채점 정정값이다. 이전 raw 기준은 64.0%였다.

## 우리가 한 일의 순서

### 1. baseline 성능 확인

처음에는 `demo_sim.py`로 demo publishing flow를 돌렸다.

`product x source + real classification` 기준 결과:

- 발행 알림: 75
- true: 27
- false: 48
- 헛알림률: 64.0%
- 케이스 도달률: 20/26

이때 `product x source`가 recall/도달률 측면에서는 가장 나았지만, 헛알림률이 너무 높았다.

### 2. 성능을 바로 튜닝하지 않고 false 원인 감사

threshold, prompt, warmup, gating을 바로 바꾸지 않았다.

먼저 false 48건을 감사했다.

초기 분해:

- CS 쪽 false가 44/48
- 색상 관련 false가 41/48
- `early_same_channel` 30건 중 day 29-32에 28건 집중

하지만 이후 지인님 피드백과 추가 검증을 통해, “CS 색상이라서 프롬프트가 문제다”라고 단정하면 안 된다는 점을 확인했다.

### 3. 채점 제외 window를 `ignored`로 분리

`config_anomaly.csv`에는 `scoring_included=N`이거나 `intended_answer`가 빈칸인 구간이 있다.

기존 `demo_sim.py`는 `intended_answer == TRUE`만 true로 보고, 나머지는 전부 false로 처리했다.

이 때문에 사전에 채점 제외로 설계한 상승 구간이 false 분자에 들어갔다.

수정:

- TRUE window: `true`
- TRUE 이후 6일 tail: `echo`
- `scoring_included=N` 또는 빈 `intended_answer`: `ignored`
- 나머지: `false`

결과:

- 기존 false-like 48건 중 6건이 `ignored`
- 공식 false는 42건
- 헛알림률은 64.0%에서 60.9%로 정정

중요: 이것은 성능 개선이 아니라 채점 기준 정정이다.

### 4. 남은 42개 false를 oracle vs real로 비교

남은 42개 false가 분류기 문제인지 확인하기 위해 oracle/golden 실행과 real classification 실행을 비교했다.

결과:

- 41개는 oracle/golden에서도 같은 날 발생
- 1개만 real classification에서만 발생

해석:

- 남은 헛알림 대부분은 프롬프트/분류기 문제가 아니다.
- 탐지 로직이 바라보는 데이터 구조와 mock 생성기의 baseline 해석 문제일 가능성이 크다.

### 5. `early_same_channel` 30건을 case-past 경계 기준으로 감사

남은 false 42개 중 가장 큰 덩어리는 `early_same_channel` 30건이었다.

이 30건은 같은 product/aspect/source/channel에 미래 TRUE window가 있는데, 그보다 평균 18.6일 먼저 발화한 알림이다.

추가 감사 결과:

- 30/30 전부 탐지기의 현재 7일 window가 미래 TRUE 케이스의 generated case-past 구간과 겹침
- 평균 overlap: 6.60일
- 평균 detector current rate: 7.93%
- 평균 pre-case-past rate: 0.62%
- 평균 generated case-past rate: 5.32%
- 평균 TRUE-window rate: 12.31%

해석:

미래 TRUE 케이스를 만들기 위해 `window_start_day - 28`일부터 `past_neg` 구간을 생성한다. 그런데 daily demo simulation에서는 이 case-past 구간이 공식 TRUE window보다 훨씬 먼저 “현재 7일 window” 안에 들어온다.

탐지기는 이 높아진 case-past 구간을 현재 상태로 보고, 더 이전의 낮은 background와 비교해 발화한다.

추가 검산 결과, TRUE case-past 33행은 config `past_rate` 및 `BASELINE_RATE`와 33/33 일치했다. 따라서 case-past가 비정상적으로 높게 심긴 것이 아니라, 주변 순수 배경이 `BASELINE_RATE`보다 약 1/6로 희석되어 경계 단차가 생긴 것이다.

따라서 가장 큰 헛알림 원인은 모델 오답이 아니라 mock 생성기의 baseline 해석 문제다.

### 6. TRUE 없는 false 12건을 추가 감사

남은 false 중 `no_true_same_product_aspect_source` 12건도 따로 확인했다.

결과:

- 12건 중 11건은 oracle/golden에서도 같은 날 발생
- 1건만 real classification에서만 발생
- 12건 중 10건은 현재 window가 관련 config의 case-past 구간과 겹침

분류:

| Category | 개수 |
|---|---:|
| 미래 채점 제외 same PAS case-past | 6 |
| 미래 scored FALSE same PAS case-past | 2 |
| 같은 상품의 다른 aspect case-past | 2 |
| 단순 config overlap으로 설명 안 됨 | 2 |

해석:

TRUE가 없어서 완전한 헛알림처럼 보였던 12건도 대부분은 configured FALSE, 채점 제외, 다른 aspect 시나리오의 case-past 영향이었다. 즉 이쪽도 threshold나 프롬프트를 먼저 고칠 문제가 아니라 mock 생성기의 baseline 해석 문제에 가깝다.

마지막으로 남은 2건은 row-level로 확인했다.

- P012 / review / 사이즈 / NAVER / day53: current 8/68 = 11.76%, past28 6/276 = 2.17%
- P022 / cs / 사이즈 / NAVER / day53: current 4/43 = 9.30%, past28 0/197 = 0.00%

두 건 모두 oracle/golden에서도 발생했으므로 real classification 문제는 아니다. 명확한 case-past overlap은 없지만, config window 밖에서 current 7일에 부정 표본이 몰린 배경 변동 또는 hot/gap 생성 영향으로 보인다.

### 7. baseline 생성 희석 문제 확인

순수 배경 상품만 따로 보면 config baseline이 전체 문의 분모 기준으로 재현되지 않는다.

예시:

| Channel | Aspect | 순수 배경 관측 | Config |
|---|---:|---:|---:|
| COUPANG | 색상 | 0.903% | 5.000% |
| NAVER | 색상 | 1.042% | 6.000% |
| ZIGZAG | 색상 | 0.972% | 7.000% |

원인:

생성기가 전체 문의에 baseline을 적용하는 것이 아니라, 먼저 aspect별로 볼륨을 나누고 그 안에서 baseline 확률을 적용한다. 그래서 전체 분모 기준으로 보면 대략 `config / aspect_count`처럼 희석된다.

중요:

추가 감사:

- TRUE config 행 33개 case-past 관측률이 config `past_neg/past_total`과 일치: 33/33
- config `past_rate`가 `BASELINE_RATE`와 일치: 33/33
- 평균 case-past 관측률: 5.03%
- 평균 순수 배경률: 0.85%
- 평균 config / 순수 배경 비율: 6.04배

중요:

이 문제는 case-past 조기 발화와 별개 원인이 아니라 같은 생성기 baseline 해석 문제다. 남은 false 42건 중 40건이 case-past overlap과 관련되어 있으므로, baseline 보정 후 헛알림 순감은 유력하다. 다만 아직 mock data를 공식 재생성해 재측정한 것이 아니므로 성능 개선 수치로 주장하면 안 된다.

## 우리가 아직 하지 않은 것

- mock data 공식 재생성 안 함
- `data/input`, `data/golden` 덮어쓰기 안 함
- threshold 조정 안 함
- prompt 수정 안 함
- warmup/shadow/gating을 성능 개선으로 채택 안 함
- 새 규칙을 최종 성능으로 주장 안 함

## 발표나 보고에서 말하면 되는 것

말해도 되는 표현:

> 실험 2 데모 결과의 초기 헛알림률은 64.0%였습니다. 이후 성능을 임의로 튜닝하기 전에 false alert를 분해했고, 사전에 채점 제외로 정의된 window 6건이 false 분자에 들어간 것을 확인해 `ignored`로 분리했습니다. 그 결과 공식 채점 기준의 헛알림률은 60.9%로 정정되었습니다. 남은 false 42건 중 41건은 oracle/golden에서도 발생했습니다. 추가 감사 결과 TRUE case-past는 config baseline대로 생성되어 있었고, 순수 배경이 약 1/6로 희석되어 case-past 경계 단차가 생긴 것으로 판단했습니다.

말하면 안 되는 표현:

> 모델 성능을 개선해서 헛알림률을 64.0%에서 60.9%로 낮췄습니다.

이 표현은 틀리다. 60.9%는 성능 개선이 아니라 채점 정정 결과다.

## 다음에 해야 할 일

1. `BASELINE_RATE`가 전체 문의 분모인지 aspect 내부 비율인지 팀과 확정한다.
2. 전체 문의 분모가 맞다면 generator의 배경 baseline 생성 방식을 보정한다.
3. `no_true_same_product_aspect_source` 12건이 진짜 false인지, golden 누락인지 검토한다.
4. 보정된 mock data를 sandbox에서 먼저 재생성해 실험 2를 재측정한다.
5. 그 뒤에도 헛알림이 높으면 threshold/persistence/gating을 별도 tuning set에서 검토한다.
6. 최종 성능은 별도 holdout 또는 재생성된 독립 평가셋에서 측정한다.
