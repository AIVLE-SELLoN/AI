# 이상탐지 운영 품질 방어막 구현 기록

작성일: 2026-08-12
작업 브랜치: `feat/detection-operational-guards`

## 목적과 범위

운영 연동 전 점검에서 확인된 리뷰 분류 누락과 원인 분석 LLM 응답 오염을 막는다.
백엔드 계약, mock 데이터, 탐지 임계값, 골든 라벨과 채점 기준은 변경하지 않는다.

## 1. CS·리뷰 분류 coverage

분류 완료 여부를 aspect 개수가 아니라 `classified_item` 부모 레코드 존재 여부로 판단한다.
워커는 정상 분류 결과가 빈 배열이어도 부모 행을 저장하고, 일일 로더는 LEFT JOIN으로
`ClassifiedItem(aspects=[])`를 복원한다. 따라서 다음 두 상태를 구분할 수 있다.

| 상태 | 부모 행 | aspect 자식 행 | 판정 |
| --- | --- | --- | --- |
| 무관 리뷰 정상 분류 | 있음 | 0개 가능 | 완료 |
| 분류 미실행·최종 실패 | 없음 | 없음 | coverage 누락 |

검사는 상품·채널·source·일자별로 수행한다. 한 문서라도 부모 레코드가 누락된 슬롯은
기존 CS 정책과 동일하게 BH 검정 전에 제외한다. 배치 로그와 실행 요약에는 제외 슬롯 수,
누락 문서 수, 슬롯별 원문/분류 건수를 남긴다.

평가 스크립트도 실제 캐시에 키가 없는 문서를 빈 aspect 완료 건으로 만들지 않도록
수정했다. oracle만 모든 문서를 분류 완료로 취급한다. 기존 정본 실험은 최종 coverage가
12,410/12,410이므로 결과 수치에는 변화가 없다.

## 2. 원인 분석 LLM 검증

원인 분석 응답에 다음 검증을 적용한다.

1. Pydantic 기반 필수 필드·타입·추가 필드 검증
2. 입력과 응답 ID의 개수 및 순서 완전 일치
3. 중복·누락·요청에 없는 ID 차단
4. 색상·사이즈·소재별 허용 cause taxonomy 검증
5. confidence 0~1 범위 검증
6. `aspect_match=true`일 때 evidence 필수
7. evidence가 실제 원문에 포함되는지 검증

입력은 최대 20건과 렌더링 문자 상한을 동시에 지키도록 순서대로 나눈다. 하나의 문의만으로
상한을 넘으면 호출 전에 실패시킨다.

## 3. 실패 격리

후보별 원인 분석을 독립적으로 보호한다. 특정 상품·aspect·채널·source 후보의 LLM 호출이나
응답 검증이 실패해도 다른 후보의 탐지는 계속한다. 실패 후보는 다음과 같이 처리한다.

- 탐지 알림 자체는 유지
- `root_cause=null`, 인용 ID 없음
- 탐지 확신도 `낮음`
- 권장 조치 `채널 운영 요소 점검 권장`
- 자동 개선안 생성 차단
- 후보 추적 키와 예외 종류를 오류 로그에 기록

즉, 원인 분석 실패를 정상 성공으로 집계하지 않으면서도 후처리 오류가 통계 탐지 결과를
전부 지우지 않게 한다.

## 백엔드 합의 후 남은 일

- `company_id`를 포함한 결정론적 alert/recommendation ID와 revision 계약
- 회사·채널·source별 수집 완료 watermark와 freshness 차단 정책
- coverage/freshness 제외 상태의 운영 저장 위치와 대시보드 노출 방식

freshness는 현재 문서의 마지막 날짜만 보고 임의로 판정하지 않는다. 문의가 실제로 없었던
날과 수집 장애를 구분할 수 없으므로, 백엔드의 수집 완료 신호가 확정된 뒤 구현한다.
