## 1. 기본 로직 (한 문단)

같은 상품에 대해 **각 채널의 각 aspect 부정 문의 비율이 그 채널의 과거 수준 대비 통계적으로 유의하게 상승했는지**를 검정하고, 윈도우 전체 배치에 **다중비교 보정(BH-FDR)** 을 적용해 발화를 확정한 뒤, **상승한 채널의 개수**로 편중형/전역형을 구분해 원인 진단 여부를 결정한다.

**"채널 비교"는 두 작업이다 — 헷갈리면 안 됨**

| 작업 | 무엇을 답하나 | 어떻게 | 단계 |
| --- | --- | --- | --- |
| **탐지** | 이 채널에 뭔가 터졌나? | **자기 과거와 비교** | [2] |
| **진단** | 이 채널만의 문제냐, 상품 전체냐? | **채널끼리 비교** | [3] |

멀티채널 플랫폼의 차별점은 **진단([3])** 이며, 이는 채널을 서로 비교해야만 나온다. 다만 탐지에 채널간 절대비교를 쓰면 **체질(평소 높은 baseline)을 병(이상)으로 오진**하므로, 반드시 ① 자기 과거로 탐지 → ② 오른 채널이 1개냐 전부냐로 진단 순서를 지킨다.

## 2. 입력 데이터

이상탐지는 **매핑이 끝났다고 가정**하고 그 이후만 담당한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `cs_id` / `review_id` | string | 문의·리뷰 고유 ID |
| `product_group_id` | string | 🔴 매핑 산출물 — **상품 그룹 ID** (구 `master_sku_code`). 필드명은 매핑팀 확인 후 확정 |
| `channel` | string | COUPANG / NAVER / ZIGZAG |
| `source` | string | cs / review |
| `raw_text` | string | 원문 텍스트 (원인 분류용, [6]단계) |
| `aspect` | string | 색상 / 사이즈 / 소재 / 파손 / 오배송 / 기타 |
| `sentiment` | int | 부정 -1 / 중립 0 / 긍정 1 (AI Hub 71603 컨벤션) |
| `created_at` | datetime | 발생 시각 (슬라이딩 윈도우 기준) |

**헷갈리면 안 되는 점**
① 주문 데이터 없음 ② 상세페이지 **내용** 없음(수정 타임스탬프만) ③ 원인은 문의 텍스트에서 **분류**(추출 아님) ④ `product_group_id`는 매핑 로직 산출물을 그대로 수신

🔴 **필드명 — 매핑팀 확인 대기:** V2.1 §7-2가 `master_sku_code`의 **의미를 "상품 그룹 ID"로 정리**한 것은 확정이다. 다만 **필드명 자체의 변경은 매핑팀 스키마 소관**이며 급하지 않다. 이름만 교체하면 되므로 로직 영향은 없다.

**분모로 주문 데이터를 쓰지 않는 이유**
판매량 정규화(부정 문의 ÷ 판매량)도 가능하나, 부정률(문의 내부 비율)만으로 "판매 급증 → 문의 동반 증가" 오탐이 자체 처리되고 주문-문의 발생 시차 문제를 피할 수 있어 현행 유지.
**인지된 한계:** 같은 상품의 무관 문의(재입고 등)가 폭증하면 분모가 부풀어 신호가 희석될 수 있다(시나리오 SC-022로 기록).

🔵 **순수 함수 분리 (구현 요구사항)[0]~[7]의 각 단계를 부수효과 없는 순수 함수로 분리**한다. 그래야 채점기가 앞단 분류기를 거치지 않고 **golden 카운트를 직접 넣어 호출**할 수 있다.
**이유:** 본채점은 oracle 기준이다(시나리오 §4). 저사건 케이스(D·G)는 분류 오차 1건에 판정이 뒤집혀 탐지 로직이 정상인데도 오답 처리되기 때문이다. **이 구조가 없으면 본채점 자체가 불가능하므로 사실상 필수다.**
별도의 "oracle 전용 모드"를 만들 필요는 없다 — 함수만 분리돼 있으면 충분하다.

## 3. 전체 파이프라인

```
[0] 집계         상품 × aspect × 채널 × source 별 부정 비율 계산
      ↓
[1] 과거 기준     각 채널의 "과거 윈도우 부정률" 확보 (알림 구간 제외)
      ↓
[2-A] 개별 검정   채널별 "현재 vs 자기 과거" p값·상승폭 산출  ← 아직 발화 결정 안 함
      ↓
[2-B] 배치 보정   ★윈도우 전체에 BH-FDR★ → 그 뒤 min_delta AND → 발화 확정
      ↓
[3] 편중/전역     ★채널 비교★ 발화 채널 수로 판정
      ↓
[4] 주 aspect     여러 aspect 동시 발화 시 delta 최대인 것 선택
      ↓
[5] 스코프 필터    개선안 생성 가능 aspect인지 판정
      ↓
[6] 원인 분류     (편중형 & 스코프 내) 문의 텍스트 → 원인 후보 분류
      ↓
[7] 결과 발행     탐지 확신도 산출 (source별)
      ↓
[8] 소스 종합     combine_sources() → 확신도·필드 채택 → 알림 1건 발행
```

**CS와 리뷰는 [0]~[6] + [7]의 확신도 산출까지 각각 독립 수행한 뒤, combine_sources()로 종합해 알림 1건만 발행한다.** 과거 기준도 source별로 분리한다.

🔵 **[2]가 두 단계로 쪼개진 이유:** BH-FDR은 **배치 전체의 p값을 정렬해서** 임계를 정하는 상대평가다. 검정 하나만 보고는 발화 여부를 알 수 없다. 그래서 [2-A]는 p값만 산출하고, [2-B]에서 배치를 모아 발화를 확정한다.

## 4. 단계별 상세

### [0] 집계 — 부정 비율

```
부정률(상품, aspect, 채널, source, 윈도우)
  =  해당 (상품, aspect, 채널)의 부정 문의 수      ← 분자
  ÷  해당 (상품, 채널)의 총 문의 수                ← 분모 (aspect 무관, 전체 문의)
```

- 🔵 **분모는 상품(product_group)×채널 총문의**다. 채널 전체도 아니고 SKU도 아니다.
    - 채널 전체로 나누면 잘 팔리는 상품의 부정 신호가 희석된다.
    - SKU로 좁히면 문의 원본에 옵션 정보가 없어 집계 자체가 불가능하고, 최소표본 규칙상 만성 보류가 된다.
- 🔵 **리뷰는 분모가 다르다.** 리뷰의 분모는 **상품×채널 리뷰 총 건수**이며 문의 수와 섞지 않는다.
- **source(cs/review)별 분리 집계.** 합산하지 않는다(분모가 다르므로).
- 집계 윈도우: 일별 슬라이딩. **현재 = 최근 7일 / 과거 기준 = 직전 28일**.
- 윈도우 합계로 집계하므로 **하루짜리 스파이크는 자연히 희석된다**(의도된 동작, 시나리오 SC-024).

### [1] 과거 기준 확보

각 채널의 **과거 윈도우 실측치**를 기준으로 쓴다. 설정값 테이블은 초기 구간 폴백용으로만 남긴다.

```python
# 채널 c, aspect a 에 대해 필요한 4개 숫자
cur_neg,   cur_total   = 현재 윈도우(최근 7일)의  (부정 건수, 총 문의 수)
past_neg,  past_total  = 과거 윈도우(직전 28일)의 (부정 건수, 총 문의 수)
```

- **기준선 오염 방지 (중요):** 알림이 발행된 (상품, aspect, 채널)의 **알림 구간 날짜는 과거 윈도우 집계에서 제외**한다.
이유: 지속되는 이상이 과거 윈도우에 섞이면 "새로운 평소"가 되어 **알림이 스스로 꺼진다.**
제외로 과거 표본이 절반 이하로 줄면 초기 구간과 동일하게 설정값 폴백.
- 과거 윈도우가 부족한 서비스 초기에만 설정값 baseline 사용.

### [2-A] 개별 검정 — 자기 과거 대비 (p값 산출)

채널간 비교가 아니라 **채널별로 "현재 윈도우 vs 자기 과거 윈도우"** 를 단측 검정한다. 각 채널이 자기 평소와만 싸우므로 채널간 baseline 차이가 판정에 끼어들지 않는다.

```python
from scipy.stats import fisher_exact

MIN_SAMPLE = 10      # 분모(총문의)가 이보다 적으면 판정 보류
MIN_DELTA  = 0.03    # 최소 상승폭 3%p — 실질적 의미 필터

def run_one_test(cur_neg, cur_total, past_neg, past_total):
    """
    검정 1건 = (한 상품, 한 aspect, 한 채널, 한 source)

    반환값에 '발화 여부'가 없다는 점에 주의.
    발화는 배치 전체를 봐야 정해지므로 [2-B]에서 결정한다.
    """

    # ── 1) 2x2 분할표를 만든다 ────────────────────────────
    #        │ 부정      │ 부정 아님
    #  현재  │ cur_neg   │ cur_total  - cur_neg
    #  과거  │ past_neg  │ past_total - past_neg
    table = [
        [cur_neg,  cur_total  - cur_neg],
        [past_neg, past_total - past_neg],
    ]

    # ── 2) Fisher 정확검정 (단측) ────────────────────────
    # alternative='greater' = "현재가 과거보다 높은가"만 본다.
    # 낮아진 경우는 이상이 아니므로 관심 없음.
    # Fisher를 쓰는 이유: 표본이 크든 작든 정확하다. z-test 분기가 필요 없다.
    _, p_value = fisher_exact(table, alternative='greater')

    # ── 3) 상승폭(delta) 계산 ───────────────────────────
    cur_rate  = cur_neg  / cur_total
    past_rate = past_neg / past_total
    delta     = cur_rate - past_rate        # 예: 0.08 이면 +8%p 상승

    return {
        "p_value":    p_value,
        "delta":      delta,
        "meaningful": delta >= MIN_DELTA,   # 실질적 의미가 있는 상승인가
    }

def build_batch(all_combinations):
    """
    윈도우 하나에 대해 '판정 가능한' 검정을 전부 모은다.

    all_combinations: [(상품, aspect, 채널, source, 카운트4개), ...]
    반환: 검정 목록 + 보류 채널 목록
    """
    batch, held = [], []

    for product, aspect, channel, source, counts in all_combinations:
        cur_neg, cur_total, past_neg, past_total = counts

        # ── 최소표본 가드 ──────────────────────────────
        # 기준은 '분모'인 (상품, 채널) 총 문의 수다. aspect와 무관하다.
        # 분모가 작으면 비율이 널뛰기 때문에 아예 판정하지 않는다.
        # (예: 3건 중 2건 = 67% 는 무섭게 보이지만 아무 의미 없다)
        # 보류는 채널 단위 → 그 채널의 모든 aspect가 함께 빠진다.
        if cur_total < MIN_SAMPLE:
            held.append((product, channel))
            continue

        result = run_one_test(cur_neg, cur_total, past_neg, past_total)
        result["key"] = (product, aspect, channel, source)
        batch.append(result)

    return batch, held
```

**규칙 정리**

- α = 0.05 (통계 표준값, 셀러 조정 불가)
- 🔵 **최소표본:** 현재 윈도우의 **(상품, 채널) 총문의** < 10이면 판정 보류(다음 윈도우 이월).
**보류는 채널 단위**다 — 분모가 작으면 그 채널의 **모든 aspect**가 함께 보류되고 [3]의 "판정 가능 채널"에서 제외된다.
- **Fisher 단측 단일화:** 표본 크기와 무관하게 정확하므로 계산기를 하나로 통일. `min(cur_neg, past_neg) < 5` 같은 분기는 근거가 없어 삭제.
- 🔵 **min_delta 3%p — 근거 정정:** 이것은 **오탐 게이트가 아니다.** 시뮬레이션 결과 오탐률 감소가 **0%** 였다(부록 A). 배경 볼륨에서 상승폭의 표준편차가 4.10%p라 3%p는 0.73 SD에 불과해, Fisher가 유의 판정할 만큼 튄 표본은 이미 3%p를 넘기 때문이다.
**실제 역할:** N이 클 때 통계적으로는 유의하지만 실무적으로 무의미한 상승(예: +0.5%p)을 거르는 **실질적 의미 필터**. 다중비교 대응은 [2-B]가 담당한다.

### [2-B] 배치 보정 — BH-FDR

```python
from statsmodels.stats.multitest import multipletests

FDR_Q = 0.05    # "발행한 알림 중 가짜가 5% 이하" 를 보장하는 수준

def decide_fires(batch, q=FDR_Q):
    """
    윈도우 전체 검정에 BH-FDR을 적용해 '발화'를 확정한다.

    왜 배치로 하나?
      검정을 상품×aspect×채널×source 조합마다 매일 돌리면 하루 약 1,464건이 된다.
      보정 없이 각각 α=0.05로 판단하면, 아무 문제 없는 정상 상품 하나도
      하루에 최소 1건 오탐할 확률이 54.8%다 (부록 A).

    BH가 Bonferroni보다 나은 이유?
      Bonferroni는 임계를 α/m 으로 일괄 축소해 참양성까지 죽인다.
      BH는 step-up 방식이라 '발견이 많으면 기준이 완화'된다.
      순위 k번째 검정의 임계는 (k/m) × q 이므로,
      진짜 이상이 여러 건 있으면 실효 컷오프가 함께 올라간다.
    """
    p_values = [t["p_value"] for t in batch]

    # rejected[i] = i번째 검정이 BH 기준으로 유의한가
    rejected, _, _, _ = multipletests(p_values, alpha=q, method="fdr_bh")

    for test, is_significant in zip(batch, rejected):
        # ── 이중 잠금 ───────────────────────────────
        # ① BH 보정 후에도 통계적으로 유의하고
        # ② 상승폭이 실무적으로 의미 있는 크기여야
        # 비로소 '발화'로 본다.
        test["fired"] = bool(is_significant) and test["meaningful"]

    return batch
```

🔵 **⚠️ 적용 순서 주의 — BH가 먼저, min_delta가 나중이다.**`batch`에는 **min_delta를 통과하지 못한 검정도 그대로 들어 있다.** BH를 **전체 검정(m = 1,464)** 에 적용한 뒤, 그 결과에 min_delta를 AND로 겹친다.

**순서를 바꾸면 안 되는 이유:** min_delta로 먼저 걸러 family를 줄이면, **관측된 delta라는 데이터에 근거해 검정 집합을 고르는 것**이 되어 FDR 보장이 깨진다. 또한 m과 순위가 달라져 컷오프 자체가 바뀐다. BH를 전체에 적용한 뒤 min_delta로 좁히는 것은 발견을 줄이기만 하므로 **보수적이고 안전**하다.

**family(보정 단위) 정의 — 확정**

| 구성 | 검정 수 |
| --- | --- |
| 케이스 상품 38개 × 36검정(6 aspect × 3 채널 × 2 source) | 1,368 |
| 배경 상품 4개 × 36검정 | 144 |
| 보류 채널 제외 — (상품,채널) 4개 × 12검정(6 aspect × 2 source) | − 48 |
| **윈도우 1회 합계** | **1,464** (42상품 1,512 − 보류 48) |
- 🔵 **평가 배치와 운영 배치에 같은 family를 쓴다.** 평가도 실제로는 모든 상품·aspect 조합을 돌리므로 규모가 동일하다. 이렇게 하면 *"채점은 통과인데 데모에선 안 뜬다"* 는 불일치가 원천 차단된다.
- **보류 채널의 검정은 family에서 제외**한다(애초에 검정을 수행하지 않으므로).
- **min_delta 탈락 검정은 family에서 제외하지 않는다**(위 주의 참조).
- 제품 언어로는 **"이번 주 발행한 알림 중 가짜는 5% 이하"** 를 보장하는 설정이다.

### [3] 편중형 / 전역형 판정 ★멀티채널 차별점★

여기가 **채널을 서로 비교하는 단계**이자 멀티채널 플랫폼의 핵심 차별점이다. [2]에서 진짜 이상만 걸러낸 뒤, 그 이상이 **한 채널만의 것(편중)이냐 전 채널 공통(전역)이냐**를 진단한다.

```python
def classify_pattern(channel_status):
    """
    channel_status: { 채널명: {"testable": bool, "fired": bool} }
       testable=False  → 표본 부족으로 판정 보류된 채널

    판정 단위는 aspect별이다.
    "쿠팡이 편중"이 아니라 "쿠팡의 색상이 편중"이다.
    """
    testable = [ch for ch, s in channel_status.items() if s["testable"]]
    held     = [ch for ch, s in channel_status.items() if not s["testable"]]
    fired    = [ch for ch in testable if channel_status[ch]["fired"]]

    # ── 아무 채널도 안 울렸으면 정상 ──────────────────
    if len(fired) == 0:
        return {"verdict": "정상", "channels": [], "held": held}

    # ── 판정 가능한 채널이 1개뿐이면 구분 자체가 불가능 ──
    # 비교 대상이 없는데 "편중"이라고 단정하면 과잉 주장이다.
    if len(testable) == 1:
        return {
            "verdict": "구분불가",
            "channels": fired,
            "held": held,
            "note": "타 채널 표본 부족 — 편중/전역 구분 불가",
        }

    # ── 판정 가능한 채널이 전부 울렸으면 전역형 ──────────
    if len(fired) == len(testable):
        # 못 본 채널이 있으면 '잠정'을 붙인다.
        # 보류 채널이 멀쩡할 수도 있으므로 전역이라 단정하지 않는다.
        verdict = "잠정 전역형" if held else "전역형"
        return {"verdict": verdict, "channels": fired, "held": held}

    # ── 일부만 울렸으면 편중형 (1개든 2개든) ────────────
    return {"verdict": "편중형", "channels": fired, "held": held}
```

**판정 규칙 요약**

| 상황 | 판정 | 후속 |
| --- | --- | --- |
| 발화 채널 0개 | **정상** | 알림 없음 |
| 🔵 판정가능 채널 1개 + 발화 | **구분불가** | 알림 발행. **[6] 원인 분류 생략**, 확신도 '중간' |
| 발화 = 판정가능 전부, 보류 채널 없음 | **전역형** | "상품 자체 점검 권장", 개선안 없음 |
| 🔵 발화 = 판정가능 전부, 보류 채널 있음 | **잠정 전역형** | 위와 동일 + "○○ 채널 표본 부족, 확정 시 재판정" 병기 |
| 발화 채널이 일부(1~2개) | **편중형** | 원인 진단 진행. **채널별로 각각 알림 발행** |
- 보류 채널이 있으면 알림에 **"○○ 채널은 표본 부족으로 판정 제외"** 를 항상 병기한다.
- 전역형에 별도 delta 임계는 필요 없다 — 각 채널이 자기 검정을 통과했는지로 판단되기 때문.

### [4] 주 aspect 선택

한 채널에서 여러 aspect가 동시에 발화하면, **자기 과거 대비 상승폭(delta)이 가장 큰 것**을 주 원인으로 삼는다.

```python
def pick_main_aspect(fired_aspects):
    """
    fired_aspects: { aspect: delta }   ← delta = 현재율 - 과거율

    예) {"색상": 0.080, "파손": 0.070}
        → main="색상"(8.0%p), sub="파손"
    """
    main = max(fired_aspects, key=fired_aspects.get)
    subs = [a for a in fired_aspects if a != main]
    return main, subs
```

- 나머지 aspect는 **부가 관찰**로 리포트에 병기한다(버리지 않는다).

### [5] 스코프 필터

편중형으로 판정된 aspect가 **개선안을 생성할 수 있는 것인지** 판정한다.
**탐지는 전 aspect 수행하고, 원인분류·개선안 생성은 스코프로 제한한다.**

| aspect | 편중 판정 | 원인 분류 | 개선안 | 셀러가 받는 것 |
| --- | --- | --- | --- | --- |
| 색상 | ✅ | ✅ | ✅ | 원인 + 개선안 |
| 사이즈 | ✅ | ✅ | ✅ | 원인 + 개선안 |
| 소재 | ✅ | ✅ | ✅ | 원인 + 개선안 |
| 파손 | ✅ |  **—** | ❌ | 알림 + "물류 점검 권장" |
| 오배송 | ✅ |  **—** | ❌ | 알림 + "운영 점검 권장" |
| 기타 | ✅ | — | ❌ | 알림만 |
- 🔵 **파손·오배송의 원인 분류를 "—"로 정정(확정).** V2.1 표는 ✅였으나 [6]에 **원인 후보가 정의되어 있지 않고**, 개선안도 없어 결과를 쓸 곳이 없다. 시나리오 §4도 root_cause 채점을 스코프 내로 한정하고 있어 충돌이 없으며, **쓸 곳 없는 분류에 LLM 비용을 쓸 이유가 없다.**
- **파손·오배송을 aspect 목록에서 빼면 안 된다.** 빼면 그 문의들이 다른 aspect로 오분류되어 신호를 오염시킨다.

### [6] 원인 분류 (편중형 & 스코프 내)

**수행 조건:** `verdict == "편중형"` **그리고** aspect가 스코프 내(색상·사이즈·소재)일 때만.
**전역형·잠정 전역형·구분불가·정상은 [6]을 수행하지 않는다.**

편중 채널의 해당 aspect 부정 문의 텍스트를 모아 **사전 정의된 원인 후보로 분류**한다(프롬프트3).
**추출이 아니라 분류이므로 정확도 측정이 가능하다.**

```
색상 :  사진_색감_오차 / 조명_보정_차이 / 실물_염색_편차 / 기타
사이즈: 표기_오타 / 실측_표기_편차 / 채널_사이즈_표준차이 / 기타
소재 :  소재_정보_누락 / 이미지_질감표현_부족 / 실제_원단_문제 / 기타
```

```python
CONSISTENT_RATIO = 0.50    # 최다 원인이 이 비율 이상이어야 "일관"
CONSISTENT_COUNT = 5       # 그리고 최소 이 건수 이상

def judge_cause(classified_causes):
    """
    classified_causes: ["사진_색감_오차", "사진_색감_오차", "조명_보정_차이", ...]
                       ← 문의 1건당 원인 1개

    반환: (주원인 또는 None, 일관 여부, 빈도표)
    """
    from collections import Counter
    freq = Counter(classified_causes)

    if not freq:
        return None, False, {}

    top_cause, top_count = freq.most_common(1)[0]
    ratio = top_count / len(classified_causes)

    # 최다 원인이 과반이고 건수도 충분해야 "원인이 일관되게 나왔다"고 본다.
    is_consistent = (ratio >= CONSISTENT_RATIO) and (top_count >= CONSISTENT_COUNT)

    if is_consistent:
        return top_cause, True, dict(freq)
    else:
        # 원인이 흩어져 있으면 특정하지 않는다 → [7]에서 확신도 낮음 경로
        return None, False, dict(freq)
```

- **`aspect_match=false` 는 집계에서 제외한다.** 프롬프트3 결과 중 다른 aspect 로 오라우팅된 문의를 걷어낸 뒤 `judge_cause`에 넣는다. 따라서 `root_cause.total`과 `evidence.inquiry_ids`는 투입 문의 전체가 아니라 **필터 통과분**이다. 탐지 결과 스키마 §3이 그 둘을 같은 집합으로 정의하므로, 걷어낸 문의를 인용 경계에 남기면 개수가 어긋나고 **Agent3가 '다른 aspect 불만'을 근거로 인용할 수 있게 된다.**
- 결과는 **빈도로 제시**한다. 예: "20건 중 14건이 사진_색감_오차(70%)"
- **"일관" 기준:** 최다 원인 비율 **≥ 50%** AND 해당 문의 **≥ 5건**. 미달이면 "원인 특정 안 됨".

### [7] 결과 발행 — 탐지 확신도, 기각 없음

```python
def decide_confidence(verdict, is_cause_consistent=None, timestamp_matched=False):
    """
    탐지 확신도를 정한다. 어떤 경우에도 '기각'은 없다 — 확신도만 달라진다.

    is_cause_consistent: [6]을 수행한 경우에만 값이 있다.
                         [6]을 건너뛴 판정(전역·구분불가)에서는 None.
    timestamp_matched:   상세페이지 수정 이력이 이상 시작일과 일치하는가
                         (보강 재료일 뿐, 판정 권한은 없다)
    """

    # ── [6]을 수행하지 않는 판정들 ─────────────────────
    if verdict in ("전역형", "잠정 전역형"):
        return "해당없음"          # 원인 진단 대상이 아님

    if verdict == "구분불가":
        # 🔵 [6]을 생략했으므로 원인 정보가 없다.
        #    편중이라 단정할 수 없으니 '중간'으로 고정한다.
        return "중간"

    # ── 여기서부터는 편중형 ──────────────────────────
    if not is_cause_consistent:
        return "낮음"              # 편중은 확실하나 원인이 흩어짐

    if timestamp_matched:
        return "높음"              # 편중 + 원인 일관 + 시점까지 일치

    return "중간"                  # 편중 + 원인 일관, 시점 미확인
```

| 상황 | 확신도 | 셀러가 받는 메시지 |
| --- | --- | --- |
| 편중형 + 원인 일관 + 시점 일치 | **높음** | 원인 + 개선안 |
| 편중형 + 원인 일관 (시점 미확인) | **중간** | 원인 + 개선안 |
| 편중형이나 원인 특정 안 됨 | **낮음** | "채널 운영 요소 점검 권장" |
| 🔵 구분불가 | **중간** | 알림 + "편중/전역 구분 불가(타 채널 표본 부족)". 원인 진단 없음 |
| 전역형 / 잠정 전역형 | 해당없음 | "상품 자체 점검 권장" |
| 정상 | — | 알림 없음 |
- 여기서의 확신도는 **탐지 확신도**(탐지·원인이 얼마나 확실한가)다.
셀러 화면(B4/B5)에 표시되는 **개선안 확신도(Agent3)와는 다른 값**이다.
**인터페이스:** Agent3에 이 탐지 확신도를 입력으로 전달하고, Agent3가 자체 캡핑 규칙에 사용한다.
- 상세페이지 수정 이력(타임스탬프)은 **확신도 보강용이지 판정 권한이 없다.** 이력이 없다고 기각하지 않는다.
- 발행 JSON의 필드 정의는 별도 문서(탐지 결과 스키마 — 이상탐지·Agent3 인터페이스 계약) 참조.

| CS | 리뷰 | 해석 |
| --- | --- | --- |
| 편중 O | 편중 O | **강한 신호** — 양 소스에서 동일 신호 확인 |
| 편중 O | 편중 X | **CS 선행 신호** — 리뷰는 시차로 아직 미반영 가능 |
| 편중 X | 편중 O | **리뷰 지연 반영** 또는 CS에 드러나지 않은 불만 |
- CS가 리뷰보다 빠른 신호다(리뷰는 배송 후 작성이라 2~5일 시차).
- 🔵 두 소스는 분모가 다르다: CS는 **상품×채널 문의 총건수**, 리뷰는 **상품×채널 리뷰 총건수**.
- 각 source는 [0]~[6]과 [7]의 확신도 산출까지 독립 수행하고, 알림 발행은 종합 후 1건만 한다.

**종합 규칙**

- 같은 (상품, aspect, 채널)에서 **CS·리뷰가 모두 발화**한 경우
→ 탐지 확신도를 **1단계 상향**한다.
(낮음→중간, 중간→높음, 높음 유지)
- **한쪽 소스만 발화**한 경우
→ 발화한 소스의 탐지 확신도를 그대로 사용하고,
해석 라벨만 병기한다.
- 확신도 상향은 **편중형**에만 적용한다.
→ 전역형·잠정 전역형("해당없음")은 제외한다.
- **주 소스는 CS**로 간주한다.
→ 양 소스가 모두 발화한 경우 CS 확신도를 기준으로 1단계 상향한다.
→ 근거: CS가 리뷰보다 빠른 신호이며, 본 문서의 기본 가정과 일치한다.

### 구현 인터페이스

`combine_sources()`는 **소스별 [7] 결과를 입력받아** 최종 탐지 확신도를 계산한다.

```python
LEVELS = ["낮음", "중간", "높음"]

def combine_sources(cs_result, review_result):
    """
    cs_result / review_result:
    {
        "fired": bool,
        "verdict": str,      # 편중형 / 전역형 / 잠정 전역형 / 구분불가
        "confidence": str,   # 낮음 / 중간 / 높음 / 해당없음
    }

    반환:
        (최종 탐지 확신도, 해석 라벨)
    """

    cs_fired = cs_result and cs_result["fired"]
    rv_fired = review_result and review_result["fired"]

    # ── 양 소스 발화 = 강한 신호 ─────────────────────
    if cs_fired and rv_fired:

        base_conf = cs_result["confidence"]
        base_verdict = cs_result["verdict"]  # 주 소스 = CS

        # 편중형만 상향
        if base_verdict != "편중형":
            return base_conf, "강한 신호(양 소스)"

        idx = min(LEVELS.index(base_conf) + 1, 2)
        return LEVELS[idx], "강한 신호(양 소스)"

    # ── 한쪽만 발화 ────────────────────────────────
    if cs_fired:
        return (
            cs_result["confidence"],
            "CS 선행 신호 — 리뷰는 시차로 미반영 가능",
        )

    if rv_fired:
        return (
            review_result["confidence"],
            "리뷰 지연 반영 또는 CS 미표출",
        )

    # ── 양쪽 미발화 = 정상 ─────────────────────────
    return None, None
```

**주의:** "구분불가"는 확신도가 우연히 `"중간"`일 수 있으므로, `confidence`만으로는 편중형과 구분되지 않는다. 따라서 **상향 제외 규칙을 정확히 구현하려면 `verdict`를 함께 전달해야 한다.**

### alert 필드 채택 규칙 (탐지 결과 스키마 §3.1과 정합)

🔵 `combine_sources()`는 **확신도만** 정한다. alert 1건의 나머지 필드(**verdict·main_aspect·root_cause·stats·stats.source**)는 아래 규칙으로 "채택 소스"의 값을 그대로 쓴다. (탐지 결과 스키마 §3.1과 동일)

| 상황 | 채택 소스 | verdict·main_aspect·root_cause·stats |
| --- | --- | --- |
| CS·리뷰 둘 다 발화 | **CS 우선** | CS 값 채택, stats.source=cs |
| CS만 발화 | CS | CS 값, stats.source=cs |
| 리뷰만 발화 | 리뷰 | 리뷰 값, stats.source=review |
- verdict가 소스마다 다를 때(예: CS=편중형·리뷰=전역형) 둘 다 발화면 **CS의 verdict를 채택**. 리뷰의 다른 판정은 source_signals에 발화 사실만 기록되고 alert verdict에는 반영하지 않는다 — 종합의 단일 진실은 CS.
- 이유: CS가 리뷰보다 빠른 신호라 주 소스. 위 combine_sources의 확신도 상향(편중형 한정)과 동일 기조.

## 6. 알림 운영 규칙

- 일별 슬라이딩이라 같은 이상이 윈도우에서 빠질 때까지 매일 재탐지된다
→ **이미 알림 발행된 (상품, aspect, 채널) 조합은 7일간 재알림 금지**(또는 해당 건 승인/반려 처리 전까지).
- 단, 부정률이 **추가로 +5%p 이상** 상승하면 갱신 알림을 허용한다.
- 이 억제 규칙은 [1]의 **기준선 오염 방지와 짝을 이룬다** — 알림 구간을 과거 윈도우에서 빼야 지속 이상이 "평소"로 굳지 않는다.
- **발행된 alert은 후속 배치가 철회·삭제하지 않는다 (2026-08-03 확정).**
    
    BH 컷오프는 배치 구성에 따라 변동하므로 **동일 데이터가 다음 윈도우에서 미발화**할 수 있다(부록 A: "실효 컷오프는 배치 구성에 따라 달라진다"). 
    
    하지만 **미발화는 "새 alert을 내지 않는다"는 뜻이며, 기존 alert의 상태를 바꾸지 않는다.**
    근거: 
    
    ① 컷오프 변동은 BH의 정상 거동인데, 알림이 나타났다 사라지면 셀러가 신뢰하지 못한다
    
    ② 개선안이 선생성으로 alert을 참조하고 있어서, alert을 지우면 **개선안만 남고 "왜 이 개선안이 생겼는지" 근거가 사라진다**(셀러 화면에 개선안은 떠 있는데 "색상 불만 5%→13%"라는 발단이 없어지는 상황) 
    
    ③ 승인/반려 처리된 건이면 처리 이력은 남는데 무엇을 처리했는지 맥락이 없어진다.
    → 구현 시 오케스트레이터는 배치 결과를 보고 기존 alert을 재판정하거나 회수하지 않는다.

## 8. 🔴 실행 아키텍처 (BH 도입에 따른 제약) — 백엔드 확인 필요

BH-FDR은 배치 연산이므로 실행 구조에 제약이 생긴다. **아래는 BH의 성질에서 논리적으로 도출한 것이며, 백엔드와 아직 논의하지 않았다.** 배치 구조 변경 비용을 확인해야 한다.

1. 🔴 **상품별 독립 실행 불가.** 한 상품만 따로 돌려서는 발화를 판정할 수 없다. **윈도우 단위로 전 상품 검정을 모은 뒤** BH를 적용해야 한다.
2. 🔴 **실행 단위 = 윈도우 1회 배치.** 스케줄러가 "전 상품 [0]~[2-A] 수행 → 배치 수집 → [2-B] BH → 상품별 [3]~[7]" 순서로 돌린다.
3. **데모 모드:** 탐지 실행 주기를 10초로 단축한다(평시 주기로는 압축 재생 종료 후 알림이 늦게 뜬다). 배치 구조는 그대로 유지한다.
4. **경계 케이스의 자기참조:** 임계 근처에 놓인 검정은 **자신이 발화하면 발견 수를 늘려 컷오프를 밀어 올린다.** 평가용 데이터에서 경계 케이스를 설계할 때는 "심고 → 컷 재계산 → 다시 심고"를 고정점까지 반복해야 한다(시나리오 정의서 §5-5).

## 부록 A. 다중비교가 필수인 근거 (실측)

**① min_delta는 오탐을 못 막는다** — 귀무가설 하 몬테카를로 20,000회, 배경 볼륨(현재 42 / 과거 168).
※ 리뷰어가 독립 재현해 **같은 결론**(감소율 0%)에 도달했다. 다만 baseline 설정이 달라 절대 수치는 다르다(리뷰어 2.42%→2.42%, 아래는 작성자 배치 기준).

| aspect (baseline) | p<0.05만 | p + min_delta | 감소 |
| --- | --- | --- | --- |
| 색상 (6%) | 2.740% | 2.740% | **0%** |
| 사이즈 (8%) | 2.725% | 2.725% | **0%** |
| 소재 (5%) | 2.300% | 2.300% | **0%** |

**이유:** 해당 볼륨에서 상승폭의 표준편차가 **4.10%p**다. 3%p는 겨우 **0.73 SD**라 노이즈 범위 안이고, Fisher가 유의 판정할 만큼 튄 표본은 이미 3%p를 넘는다 → **min_delta가 non-binding**. 12%p까지 올려야 효과가 나는데 그러면 참양성(상승폭 4~8%p)이 전부 죽는다.

**② 보정 없으면 오탐이 확실히 발생한다**

| 범위 | 하루에 최소 1건 오탐할 확률 |
| --- | --- |
| 정상 상품 1개 (36검정) | **54.8%** |
| 배경 상품 4개 | **95.8%** |
| 전체 42개 상품 | **~100%** |

**③ Bonferroni는 부적합** — 1,464검정 기준 α ≈ 3.4e-5로 참양성이 죽는다. BH는 step-up이라 발견 수만큼 기준이 완화된다.

🔴 **실효 컷오프 수치는 배치 구성에 따라 달라진다.** 하나로 못 박으면 안 된다.

| 배치 조건 | 실효 컷오프 |
| --- | --- |
| 작성자 배치 (보강 전 / 후) | 0.000601 / 0.000821 |
| 리뷰어 배치 | 0.0005 ~ 0.0006 |
| 리뷰어 배치 + 경계(G) 케이스 포함 | 0.0011 |

컷오프는 **귀무 검정의 p값 분포에 민감**하고, 경계 케이스를 심으면 **그 자신이 발견 수를 늘려 컷오프를 밀어 올린다**(자기참조). 최종값은 실 배치로 확정해야 한다.
