# 현진님 전달용: hybrid eval set 검증 결과

작성일: 2026-08-06

## 결론

전달해주신 hybrid eval set과 검증 스크립트는 repo 기준 위치에 반영했고, 실제 실행 검증까지 완료했습니다.

초기 실행에서는 `relabel_300` 배치 응답 중 15건이 누락됐지만, 이는 데이터 파일 문제라기보다 batch LLM 응답에서 일부 `item_id`가 빠진 문제였습니다. `scripts/verify_hybrid_eval_sets.py`에 누락 ID 재시도 로직을 추가했고, 최종 재실행에서는 `relabel_300`, `llm_generated_700` 모두 `n_failed=0`으로 채점됐습니다.

최종 기준 결과 파일:

- `eval/results/hybrid_verify_20260806_144446.json`

| 평가셋 | Aspect F1 | Sentiment Accuracy | Negative Precision | Negative Recall | Negative FPR |
|---|---:|---:|---:|---:|---:|
| relabel_300 | 0.7156 | 0.8865 | 0.7766 | 0.8902 | 0.1005 |
| llm_generated_700 | 0.9614 | 0.6605 | 0.7262 | 0.8319 | 0.4609 |

## 해석

`relabel_300`은 실제 리뷰 기반이라 aspect 분류가 훨씬 어렵게 나타납니다. 특히 자연어 리뷰에서 `핏`, `통`, `원단`, `색감`, 배송/가격/디자인 언급이 섞일 때 모델이 목표 aspect를 놓치거나 `기타`를 추가하는 패턴이 많습니다.

`llm_generated_700`은 aspect F1은 높지만 sentiment accuracy와 negative FPR이 좋지 않습니다. 특히 "파손되면 어떻게 하나요?", "혹시 안전한가요?" 같은 가정형/문의형 문장을 부정으로 볼지 중립으로 볼지 라벨 기준이 흔들리는 것으로 보입니다. 따라서 generated set의 sentiment 라벨은 최종 성능 판단 기준으로 바로 쓰기 어렵고, 정책 정리 또는 재라벨링이 필요합니다.

## 현 시점에서의 판단

이번 검증으로 평가 실행 안정성 문제는 해결됐습니다. 다만 성능 개선 실험 기준선으로 쓰려면 다음 구분이 필요합니다.

- `relabel_300`: 실제 리뷰 기반 성능 기준선으로 사용 가능
- `llm_generated_700`: aspect coverage 확인용으로는 사용 가능
- `llm_generated_700` sentiment: 라벨 정책 검토 전까지 최종 성능 지표로 사용 주의

## 추가로 부탁드릴 확인

generated sentiment 라벨 정책 중 아래 케이스를 부정/중립 중 어디로 통일할지 확인이 필요합니다.

- 아직 실제 문제가 발생하지 않은 가정형 질문
- 안전/파손/오배송 가능성을 묻는 예방형 질문
- "걱정된다", "괜찮나요?"처럼 불안 표현은 있으나 실제 경험 불만은 아닌 문장

이 기준이 정리되면 실무용 오탐률과 탐지율을 더 안정적으로 맞출 수 있습니다.
